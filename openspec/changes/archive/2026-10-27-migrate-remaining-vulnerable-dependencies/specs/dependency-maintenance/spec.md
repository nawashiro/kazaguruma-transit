# Spec Delta

## Purpose

依存更新を検証した単位で採用し、不具合のある経路だけを取り消すための条件を定める。利用者向けの動作と、元データから交通キャッシュを再生成する機能を、依存の移行後も保つ。

## ADDED Requirements

### Requirement: 検証済みの段階を独立して採用する

作業者は互換範囲の10パッケージ、GTFS経路、Google Maps経路、Prisma経路の順で変更を検証しなければならない（MUST）。採用する各段階を独立したコミットで記録する。

#### Scenario: 段階の変更を採用する

- **WHEN** 対象段階の監査と機能検証が成功する
- **THEN** 作業者は対象段階の変更と検証結果をコミットする
- **AND** 次の段階は直前に採用した状態から開始する

### Requirement: 不具合のある経路だけを取り消す

作業者は追加3経路のいずれかで動作不良を確認した場合、その経路の変更を取り消さなければならない（MUST）。前段階までの採用済み変更を維持し、失敗の理由と残存警告を記録して次の経路へ進む。検証不足の経路を成功として採用しない。

#### Scenario: 経路の移行で検索が失敗する

- **WHEN** ある経路の移行後に、移行前は成功した経路検索が失敗する
- **THEN** 作業者はその経路の変更だけを取り消す
- **AND** 直前の採用状態で該当検証が成功することを確認する
- **AND** 後続の経路は取り消し後の状態から試す

#### Scenario: 必要な実行環境が使えない

- **WHEN** 環境や認証情報が不足し、代替検証でも対象変更の互換性を判断できない
- **THEN** 作業者は未検証と未採用の理由を記録する
- **AND** その経路の試行差分を残さず、後続の独立した経路へ進む

### Requirement: 更新後も利用者向けの入出力を保つ

システムは依存更新後もGTFS取込、経路検索、地図、画像、PDFの既存の入出力を保たなければならない（MUST）。APIの認証、入力制限、エラー処理、PDFの内容と用紙設定を維持する。

#### Scenario: 更新後に既存形式の入力を処理する

- **WHEN** 利用者が既存形式で経路検索、地図取得、PDF生成を実行する
- **THEN** システムは既存形式の結果を返す
- **AND** 不正入力は既存の入力制限とエラー処理に従う

### Requirement: 交通キャッシュを空の状態から再生成する

システムは設定された保存先に空の交通キャッシュを構築し、GTFSを取り込み、経路検索を提供しなければならない（MUST）。旧DBの保持、データ移行、旧クライアントとの互換動作を要求しない。構築、取込、検索は同じ設定済みDBを使う。

#### Scenario: キャッシュが存在しない状態から起動する

- **WHEN** 作業者が旧キャッシュのない隔離環境で通常の構築・起動手順を実行する
- **THEN** システムは設定された保存先にDBを構築してGTFSを取り込む
- **AND** 取込後のデータで停留所、便、運行日を使う経路検索が成功する

#### Scenario: キャッシュを再生成する

- **WHEN** 作業者が隔離環境のキャッシュを破棄して通常の構築・起動手順を再実行する
- **THEN** システムは元のGTFSから再び検索可能なDBを生成する
- **AND** 作業用DB以外のファイルを削除しない

### Requirement: 監査と未検証事項を段階ごとに報告する

作業者は各段階の採用または取消し後に、全依存と開発依存を除く監査結果を記録しなければならない（MUST）。報告は対象の解決値、検証結果、残存警告の依存経路と理由を含む。ローカル検証を本番反映の完了として扱わない。

#### Scenario: 一部の経路を採用しない

- **WHEN** 作業者が一部の移行を取り消して他の移行を採用する
- **THEN** 最終報告は採用したコミットと取り消した経路を示す
- **AND** 取り消しによって残る警告と未検証事項を明記する
- **AND** 全脆弱性を解消したと報告しない
