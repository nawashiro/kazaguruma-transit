# Design

## Context

動機と変更範囲は [proposal.md](proposal.md) に、受入条件は [交通キャッシュの仕様](specs/transit-cache-lifecycle/spec.md) に示す。

現在の `dev`・`build`・`start` はPrisma生成、DB初期化、GTFS取込を順に実行する。`initialize-transit-cache.ts` はDBファイルがない場合だけスキーマを作る。`import-gtfs.ts` は事業者データがあれば取込を終了するため、入力やスキーマの更新を確認しない。

Prisma、GTFS取込、アプリは設定の `sqlitePath` を共有する。DBには交通データと `RateLimit` が同居し、GTFS取込はPrismaモデルにない `shapes` などのテーブルも作る。`TransitManager.prepareGTFSData()` は本番の呼出元がなく、別の取込処理と失敗後の継続処理を持っている。

静的な場所ページは場所データを参照し、交通データはAPI経由で参照する構成である。交通DBをビルド時に取り込む必要は、現在のページ生成処理からは見当たらない。

## Goals / Non-Goals

**Goals:**

- 起動前のCLI処理に再生成を集約し、アプリがDBへ接続する前に完了させる。
- スキーマ作成とGTFS取込の順序を固定し、Prisma管理外のGTFSテーブルも保持する。
- 設定先が独自のパスでも、削除・作成・取込・実行時参照を一致させる。

**Non-Goals:**

- DBのデータ移行、旧DBの退避・復旧、稼働中の時刻表差替えは扱わない。
- 入力のハッシュや更新日時による再利用判定、スキーマバージョン管理、定期取得は追加しない。
- 同じ `sqlitePath` を複数の稼働プロセスで共有する構成は扱わない。

## Decisions

### 再生成コマンドを一つにする

`npm run import-gtfs` の実体に再生成全体をまとめ、`dev` と `start` から配信開始前に呼ぶ。既存の初期化処理はこのコマンドから使う内部処理へ統合する。独立した「存在しないときだけ作る」起動経路は残さない。

処理順は、設定と入力パスの確認、DBと `-wal`・`-shm`・`-journal` の削除、親ディレクトリ作成、Prismaスキーマ作成、GTFS取込、検証とする。存在しないファイルの削除は成功扱いとし、削除権限などのエラーは中止する。ディレクトリの再帰削除は使わない。設定ファイルとローカルGTFS入力を削除対象にしない。

Prismaスキーマ作成には同じ設定を参照する `prisma.config.ts` と既存の `db push` を使う。空のDBにスキーマを作ってからGTFSを取り込み、取込後に `db push` は実行しない。これによりGTFSが追加したテーブルをスキーマ同期で消す処理を避ける。DBの読取や接続は削除とスキーマ作成を終えてから行い、処理終了時に接続を閉じる。

初期化と取込を別々に起動スクリプトへ並べる案は、単独取込との動作差が残るため採らない。インメモリDBへ置き換える案も、CLIとアプリが別プロセスで同じDBを使う構成に合わないため採らない。

### 取込成功と利用可能性を分けて検証する

現在の必須データ件数の検証を保ち、`calendar` または `calendar_dates` のいずれかにデータがあることを確認する。さらに `RateLimit` を読み書きできるスキーマがあることを検証する。テストでは再生成後のカウンターが空であり、記録もできることを確認する。

既存のfixtureテストで、運行日例外、先頭ゼロを含むID、GTFSの追加テーブルが保たれることも確認する。単に停留所と路線が存在するだけの検証には置き換えない。

### 失敗した再生成から配信へ進めない

再生成は失敗を非ゼロの終了状態として返し、`dev`・`start` は成功した場合だけNext.jsを起動する。途中のDBは配信用に使わず、次の起動時に再び破棄する。エラー出力では既存のURL等の秘匿処理を維持する。

一時DBを検証後に切り替える案と旧DBへの復帰は採らない。今回は停止中にキャッシュを作るため、可用性を保つ差替え機構や退避ファイルは必要ない。

### ビルドは交通DBを準備しない

`build` からDB初期化とGTFS取込を外し、Prismaクライアントの生成とNext.jsのビルドを行う。場所データの生成など既存の別入力処理は継続する。APIモジュールの評価だけでDBを作成・更新する箇所があれば、実際のリクエスト処理時の接続へ寄せる。

Dockerでもビルド時のGTFS取込を前提にせず、コンテナの `npm start` で再生成する。ホストのDB・SQLite付随ファイルをイメージへコピーしないよう対象の除外を確認する。ビルド専用のDBを追加する案は、不要な取込経路を増やすため採らない。

### 未使用の取込経路を除去する

`TransitManager.prepareGTFSData()` と、この取込経路だけが使う `skipImport`、入力ディレクトリ等を参照確認のうえ除去する。検索処理や通常のDB接続まで変更しない。手動再生成の案内はアプリ停止中の `npm run import-gtfs` に統一し、通常の更新はGTFS入力更新後の再起動とする。

## Risks / Trade-offs

- 起動時の取得元障害でサービスを開始できない → 非ゼロで終了し、取得元を復旧してから再起動する。ネットワーク依存を避けたい運用では既存のローカルGTFS入力を使える。
- 再生成の時間だけ配信開始が遅れる → 起動前処理として扱い、取込の成功を待つ。固定の所要時間は保証しない。
- 再起動でAPIレート制限の記録が消える → 合意済みの寿命として仕様と運用手順に明記する。制限値自体は変更しない。
- 稼働中の手動再生成や同じDBを使う同時起動で接続が競合する → 再生成はアプリ停止中に行い、稼働プロセスごとに別のDBパスを使う。ロックや無停止切替は追加しない。
- DB配置先の権限不足で起動に失敗する → 削除・作成の失敗を終了状態へ伝え、別パスでの実行もテストする。

## Migration Plan

1. アプリを停止し、GTFS入力と設定を配置して新しいコードを起動する。旧DBの手動削除や移行は不要である。
2. 再生成と検証が成功したことを確認して配信を開始する。時刻表の更新も同じ停止・再起動の手順を使う。
3. コードを戻す場合はアプリを停止し、設定先のDBとSQLite付随ファイルを削除してから、戻すコードの初期化・取込手順でキャッシュを作る。旧コードは既存DBを再利用するため、ロールバック時には削除が必要となる。
