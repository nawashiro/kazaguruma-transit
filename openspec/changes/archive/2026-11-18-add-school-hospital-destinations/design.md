# Design

## Context

- `data/destinations.json`は公開JSON-LDの`urn:uuid:`を参照する目録で、現在70件を持つ。このうち22件が`includeInRouteForm: true`である。
- 公開JSON-LDは103 recordを持つ。ローカルの交通DB（79停留所）と補正徒歩距離500mで判定すると、候補は85件になる。前回の目録更新後に15件増えた。
- 増えた15件は`gif-poi`コード1503（小学校）が8件、1601（病院）が6件、1011（映画館）が1件である。
- ルートページは`includeInRouteForm: true`のentryだけをビルドartifactから表示する。カテゴリ名と並び順は、ビルドが取得するカテゴリ名辞書から`gif-poi`コードで決まる。
- 要件レベルの振る舞いは変えない。仕様の差分は`skip_specs`で省く。

## Goals / Non-Goals

**Goals:**

- 目録を現行の公開データに一致させ、小学校8件と病院6件をルートページの選択肢へ加える。
- 既存entryの名前と掲載選択を保つ。

**Non-Goals:**

- 映画館の掲載。
- 目録更新の自動化や定期実行。
- artifact生成と表示UIの変更。

## Decisions

### 目録は更新CLIで再生成する

`npm run update-destinations`を実行し、そのあと小学校8件と病院6件だけを`includeInRouteForm: true`へ変える。CLIは候補の抽出、OSM名の解決、IDによる掲載選択の引き継ぎを実装済みで、手作業で同じ判定を再現する必要がない。

CLIは新しい候補を`false`で追加するため、映画館1件も未掲載のまま目録へ入る。ルートページには表示されないので許容する。

代替として14件を手で追記する案は、500m判定を手作業で再現することになり、次回の更新で差分がずれるため採らない。

### 掲載するのは小学校と病院に限る

映画館は今回の依頼に含まれないため、`false`のまま残す。カテゴリを追加するコードや設定は書かない。コード1503と1601はカテゴリ名辞書に存在するため、掲載すればビルドが「小学校」「病院」を出力する。

### コードとテストは変えない

表示は既存のartifact生成とUIが担う。データ固有の件数や施設名をテストへ書くと、公開データの更新のたびに壊れる。検証はビルド後のartifactで行う。

代替として生成器に「小学校と病院を自動掲載」を足す案は、仕様が定める明示的な選択と新しい候補の既定`false`に反するため採らない。

### OSM名をそのまま表示する

仕様が表示名にOSMの`name`を要求し、目録の名前を表示に使わないと定めている。`千代田区立 九段小学校`のような空白を含む表記も、そのまま表示する。表記の正規化はこの変更の範囲外とする。

## Risks / Trade-offs

- [公開データや停留所DBが計画時から変わり、候補の内訳が変わる] → 実行時に`追加:`の件数と内訳（15件、小学校8、病院6、映画館1）を確認し、違えば差分を調べる。
- [掲載entryのOSM名が解決できず、ビルドがそのentryを外す] → artifactで8カテゴリ、35件、小学校8件、病院6件を確認する。
- [映画館が未掲載候補として目録に残る] → ルートページには出ない。次回の掲載判断まで候補として保つ。
- [OSM名の表記に空白や揺れがある] → 表示名の正規化は別changeで扱う。

## Migration Plan

1. `npm run update-destinations`で目録を再生成する。
2. 小学校8件と病院6件の`includeInRouteForm`を`true`にする。
3. `npm run build`でartifactを再生成し、件数とカテゴリを確認する。
4. ルートページで「小学校」と「病院」のカテゴリ、各施設を確認する。
5. 問題があれば`data/destinations.json`の変更を戻し、再ビルドする。
