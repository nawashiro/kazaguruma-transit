# Design

## Context

現行のジオコーディングは `/api/geocode` がGoogle Maps Geocoding APIへ問い合わせ、返ってきた先頭の `formatted_address` をそのまま地点名として表示する。検索語に「千代田区」が含まれない場合は前置きする補完があり、GPSの逆引きも同じ経路を使う。

実測した制約を以下に記す。動機は proposal.md - Why を参照。

- 千代田区の既存データは、場所artifact 87件、OSMタグミラー 106件、GTFS停留所 79件。施設名はほぼ揃うが、駅名はOSMの `railway=station` に依存する。
- 東京都のOSM抽出（`https://osm.download.movisda.io/admin/JP-13-latest.osm.pbf`、133MB、毎日更新）を町字ポリゴンで切り出すと、名前付き要素は 26,753件。線形要素を除くと 21,338件、名前×街区で集約して 19,647件、JSON で約1.3MB。
- 国土交通省「位置参照情報」の千代田区街区レベル（`https://nlftp.mlit.go.jp/isj/dls/data/24.0a/13101-24.0a.zip`、33KB、Shift_JIS CSV）は1,753点、1,398街区キー、町字115種。全点が既存の町字ポリゴン（`townGeoJsonUri`、59フィーチャー）の内側に入る。
- OSMの `addr:*` タグを持つ要素は5,771件あるが、街区キーに解決できるのは1,178件（20%）だけ。`addr:neighbourhood` が「2丁目」だったり「2」だったりと揺れが大きい。
- 共有のレート制限は1時間60回で、`/api/geocode` と `/api/transit` が同じバケツを使う。

## Goals / Non-Goals

**Goals:**

- 検索・逆引きをサーバー内の索引だけで完結させ、実行時に外部へ問い合わせない。
- 番地検索を街区代表点の精度で返す。
- 名前検索で駅・公共施設を上位に、チェーン店を下位に並べる。
- 索引更新を作業者の明示的なコマンドに分離し、ビルドを外部APIに依存させない。

**Non-Goals:**

- 千代田区外の住所解決。区外の座標は逆引きで住所を返さない。
- ローマ字・かなによる検索の網羅。索引にある表記だけを照合する。
- 地図タイルの配信、経路の徒歩ルーティング。これらは #151 の範囲。
- PDFの静的画像とGoogleマップへのリンク。別issueで扱う。

## Decisions

### 索引は生成物をリポジトリに置き、更新を別コマンドにする

`data/geocode-index.json` を追跡し、`npm run update-geocode-index` で再生成する。`data/destinations.json` と同じ扱い。

133MBの抽出をビルドのたびに落とす案は却下。ビルド時間とネットワーク依存が増え、上流の提供元が止まれば全ビルドが失敗する。索引の中身は日単位でしか変わらず、都度取得する理由がない。

代替として、抽出をビルドキャッシュに置いて差分だけ取得する案も検討したが、PBFは差分取得の仕組みを持たず、実装が複雑になる割に利得がない。

### 番地は位置参照情報、名前はOSMを使う

役割を分ける。

| 用途 | 出典 | 理由 |
|---|---|---|
| 番地の解決 | 位置参照情報 | OSMの `addr:*` は街区キーへの解決率が20%しかない |
| 名前の解決 | OSM抽出・artifact・GTFS | 位置参照情報は地名と街区だけで、施設名を持たない |

東大ジオコーダ（jageocoder）は却下。実測で固有名詞を解決できず（「ニコライ堂」を千葉県旭市「ニ」に誤マッチ、「えみふる」は0件）、本番の実行経路にPythonランタイムを追加する必要もある。

### 索引の粒度は「名前 × 街区」で集約する

名前付き要素をそのまま並べると、ファミリーマート198件、セブン-イレブン173件が個別の候補として並ぶ。名前と最近傍街区の組で集約すると19,647件、1.3MBに収まり、同じ地点の重複（建物とその中の店舗）もまとまる。

集約キーは `名前` `街区` の2つ。座標は街区代表点を使い、要素の重心は使わない。街区代表点のほうが「その住所のどこか」を示す用途に合い、逆引きとも座標系が揃う。

### 照合は町名の丁目の有無を索引側から判定する

`霞が関1-1` は霞が関一丁目1番、`神田和泉町1` は神田和泉町1番。同じ `1-1` でも意味が違う。索引の町名に丁目の系列があるかどうかで解釈を切り替える。

```
入力 -> 正規化（全角数字・漢数字丁目・番地/号の区切り）
     -> 最長一致する町名を索引から選ぶ
     -> その町名が丁目を持つか判定
        持つ   : 続く数字を丁目、次の数字を街区とする
        持たない: 続く数字を街区とする
     -> 街区が一致すれば代表点、しなければ町名の代表点
```

町名の最長一致は、`神田` と `神田和泉町` のような包含関係で誤らないために必要。

### 順位付けは種別の優先度と一致種別の2段

種別の優先度を先に、一致種別を次に効かせる。逆にすると、部分一致した駅が完全一致した店舗より上に来てしまう。

| 優先度 | 種別 |
|---|---|
| 1 | 駅、公園、公共施設、文化施設、医療機関 |
| 2 | 学校、福祉施設、宿泊 |
| 3 | 物販、飲食、駐車場、その他 |

一致種別は完全一致、前方一致、部分一致の順。並び順が決まらないときは名前の文字数が短い順、次に座標の安定順（緯度・経度）で決め、同じ入力に対して同じ順序を返す。

### 逆引きは最近傍の街区代表点

1,753点の線形探索で十分。緯度経度の平面近似（経度に `cos(lat)` を掛ける）で距離を測り、最も近い街区代表点の住所を返す。千代田区の範囲外（町字ポリゴンの外）の座標には住所を返さない。

**索引の外に出た座標を「千代田区のどこか」に丸めない**のが要点。区外の座標に区内地名を付けると、利用者を誤った場所へ導く。

### 検索APIの形を変える

```
GET /api/geocode?q=霞が関1-1         -> { success: true, results: [{name, address, lat, lng, kind}] }
GET /api/geocode?lat=35.69&lng=139.75 -> { success: true, location: {lat, lng, address} }
```

`results` を最大5件返し、`q` が番地として解決できたときは1件だけ返す。既存の `address` パラメーターは受け付けない。呼び出し元はすべて本リポジトリ内にあり、外部に公開した契約ではない。

### レート制限は共有バケツのまま上限を600回/時へ

`/api/geocode` は入力確定のたびに呼ばれるため、60回/時では経路検索を数回試しただけで使い切る。600回/時は1分あたり10回に相当し、通常の操作では当たらない。

バケツを分ける案は却下。`rate_limits` テーブルは `ip` を主キーにしており、種別ごとのバケツにはスキーマ変更が要る。上限を上げるだけで乱用の抑止という目的は満たせる。

### 到達不能な地図ヘルパーを削除する

`src/lib/maps/staticMap.ts`、`src/lib/maps/directions.ts`、`src/utils/maps.ts` の非同期URL生成関数は呼び出し元を持たない。`IntegratedRouteDisplay` と `StopTimeDisplay` が使うのは同期のリンク生成関数だけ。憲章の「使わないコードを破壊的に除去する」に従って消す。

## Risks / Trade-offs

- [OSM抽出の提供元が停止する] → 索引は既にリポジトリにあり、ビルドは影響を受けない。更新コマンドが失敗するだけ。代替としてBBBike（`https://download.bbbike.org/osm/bbbike/Tokyo/Tokyo.osm.pbf`、92.8MB）に切り替えられるよう、抽出元URLを設定に置く。
- [OSMの帰属が不完全] → 名前索引はODbL-1.0の派生データベースになる。ライセンスページに出典を追加し、索引ファイルの先頭にメタ情報として出典と生成日時を書き込む。
- [チェーン店が候補を占める] → 種別の優先度で下位に沈める。それでも候補5件を埋める場合は、名前の完全一致を優先する規則が効く。
- [駅名の表記ゆれを取りこぼす] → 末尾「駅」の除去だけでは「四谷」と「四ツ谷」のような揺れは吸収できない。索引の別名タグ（`alt_name`、`official_name`、`name:ja`）を照合対象に含めることで緩和する。かな検索は本変更の対象外。
- [索引が古くなる] → 更新日時を索引に持たせ、作業者が `npm run update-geocode-index` を実行する運用にする。自動更新はしない。

## Migration Plan

1. 索引生成スクリプトと索引ファイルを追加し、`data/geocode-index.json` を追跡対象にする。
2. 照合ライブラリを追加し、`/api/geocode` を索引探索へ差し替える。クライアントが候補配列を扱えるようになるまで、APIは両方の形を返さない。呼び出し元3箇所を同時に更新する。
3. レート制限の上限を上げ、利用制限画面の文言を追随させる。
4. 旧経路（Google Mapsクライアント、`address` パラメーター、`rate_limited` 分岐のうち到達不能になったもの）を削除する。
5. 到達不能な地図ヘルパーと依存を削除する。

ロールバックは索引ファイルとAPIの差分を戻すだけで済む。外部サービスの設定変更を伴わない。
