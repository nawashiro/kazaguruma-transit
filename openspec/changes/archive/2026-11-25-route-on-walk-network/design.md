# Design

## Context

動機は proposal.md - Why を参照。現状の実装は `src/lib/transit/walking.ts` と `src/lib/transit/stop-selection.ts` にあり、どちらも直線距離に `Math.SQRT2` を掛けて徒歩距離とする。この値を候補絞り込み（`selectNearbyStops`）、従来経路の上限判定、周辺バス停経路の全組み合わせ、`NearbyStop.distance` 経由の表示上の徒歩時間が共有している。

外側の制約として、次の点を実測で確認した。以降の決定はここから導いている。

| 制約 | 実測 |
|---|---|
| 歩行ネットワークの規模 | 町字ポリゴン内＋停留所から300m以内で、28,105ノード・34,650エッジ・約518km。連結構成は120個、最大成分が98%を占める |
| artifactの大きさ | ノードとエッジを1行1要素で書くと1.96MB（gzip 438KB）、62,763行 |
| 停留所の接続距離 | 79停留所すべてが最大成分に乗り、最寄りノードまでの距離は中央値13m、最大44m |
| 点から道までの隔たり | 区の内側の任意の点では99%が342m以内。皇居など大きな敷地ではさらに離れる |
| 経路の長さ | 直線距離に対する徒歩距離は中央値1.24倍、90パーセンタイル1.64倍、99パーセンタイル2.72倍。√2=1.41は中央値より大きく、右裾より小さい |
| 探索の費用 | artifactの読み込みと隣接リスト構築が61ms。25,000ノードのダイクストラが8.5ms。停留所のスナップはグリッド索引で0.69ms/点、線形走査で10.5ms/点 |
| 500m判定の変化 | 標本200地点で、候補が一致438、直線のみ52、ネットワークのみ87。最寄り停留所は30%の地点で変わる |
| 階段の扱い | 候補経路の9.3%が階段を含む。そのうち23%には階段を避ける経路がない |
| 既存のOSM抽出 | `data/.cache/JP-13-latest.osm.pbf`（133MB）を地点索引の更新が使う。`osm-pbf-parser` は既存の依存 |

## Goals / Non-Goals

**Goals:**

- 徒歩距離を1つの関数に集約し、候補・順位・徒歩時間・目録・PDFが同じ値を共有する。
- artifactをリポジトリで管理し、差分をレビューできる形にする。
- 地図に実際の徒歩経路を描く。

**Non-Goals:**

- 段差・勾配・幅員による評価。歩行空間ネットワークデータ（PDL-1.0）は千代田区内の収録が4.5%しかなく、全区の評価に使えない。OSMの `wheelchair` は歩行ウェイ21,006本に対して56本である。
- 階段を避ける代替経路の表示。データは階段フラグを1バイト足すだけで持てるが、使う画面がない。
- 目的地目録の母集団の再設計。判定だけを同じ関数へ寄せる。

## Decisions

### 1. artifactはOSMノードIDで書き、長さは持たない

`data/walk-network.json` は `nodes: [osmNodeId, lat×10^6, lng×10^6]` と `edges: [osmNodeA, osmNodeB]` を持つ。エッジの長さは両端の座標からハバーサインで求める。

内部の通し番号で書く案は却下。ノードが1つ増えると以降の番号が全部ずれ、artifactの全行が差分になる。OSMノードIDは安定した識別子で、差分は変更された道だけに現れる。レビューでは「どの道がネットワークに入ったか」をOSM上で確認できる。

エッジの長さを保存する案（`[a, b, 350]`）も却下。再計算すれば同じ値が出るため、保存すると座標と長さが食い違いうる余地を残すだけになる。浮動小数点の差は探索の順序を変えない。

wayのref列を保存する案は、artifactの大きさがほぼ同じ（1.55MB対1.47MB、内部番号の場合）で、隣接リストを毎回組み直す手間が増える。エッジ列を採る。

座標は緯度経度を10^6倍した整数で持つ。1e-6度は約11cmで、歩行の判定に十分である。

### 2. 範囲は町字ポリゴン＋停留所300m、最大成分だけ

ノードは千代田区の町字ポリゴンの内側、またはいずれかの停留所から300m以内にあるものを含める。エッジは両端が範囲内のものだけを残し、最後に最大の連結成分だけを残す。

ポリゴンの内側だけにすると、新日本橋駅のように建物の下にある停留所が最寄りノードから215m離れる。区の外を通る歩道で駅につながっているためで、徒歩距離が実際より短く出る。停留所から300mの余白を足すと、停留所の接続距離は最大44mに収まる。

余白を大きくする案（区の外を一律500m）は却下。ノードが62,528、artifactが3.3MB（gzip 775KB）に増え、探索も32.8msへ伸びる。得られる経路の差は、範囲を広げても中央値で0%、99パーセンタイルで7.4%であり、費用に見合わない。

最大成分に限るのは、つながらない歩道を残すと「そのノードへは行けない」という結果が増え、候補判定が不安定になるためである。区の内側の任意の点2000のうち、最寄りノードが最大成分にないのは7.4%だが、そのほとんどは最大成分まで数十mで届く。

### 3. 探索は2回、接続区間は距離に含める

徒歩距離は、起点から最寄りノードまでの直線距離、ネットワーク上の最短距離、到着点の最寄りノードから到着点までの直線距離の和とする。

接続区間を除く案は却下。区の内側の点でも99%が最寄りノードから342m以内にあり、大きな敷地では数百m離れる。除くと「道の上にない点」の徒歩時間が実際より短く出る。

探索は、出発地の最寄りノードから1回、目的地の最寄りノードから1回の計2回で足りる。停留所は79件あるが、出発側のダイクストラの距離配列から全停留所の距離を一度に読める。停留所ごとに探索する案は79倍の費用になる。

ノードのスナップには、緯度経度を約111mのセルに切ったグリッド索引を使う。全ノードの線形走査は1点10.5msで、停留所79件と検索2点を合わせると0.8秒かかる。グリッド索引は0.69ms/点で、実装は30行程度である。

隣接リストは、artifactの読み込み時に圧縮行格納（CSR）へ組み直す。`JSON.parse` と構築で61ms、プロセス内に1度だけ行う。

### 4. `NearbyStop.distance` の意味は変えず、徒歩時間を明示的に持たせる

`NearbyStop.distance` は直線距離のままにする。代わりに、経路結果の停留所へ `walkingTimeMinutes` を足し、表示はその値を使う。

`distance` を徒歩距離に読み替える案は却下。同じ型が半径一覧の応答にも使われており、半径一覧は直線距離を返す契約だから、1つの項目に2つの意味が生まれる。表示側は `calculateWalkingTimeMinutes(stop.distance, ...)` で√2を掛けており、ここへ徒歩距離を渡すと二重に補正される。

`calculateWalkingTimeMinutes` は、距離をそのまま歩行速度で割る関数へ変える。`calculateGridWalkingDistanceKm` は削除する。呼び出し元は経路検索と表示の2箇所だけで、どちらも徒歩距離か徒歩時間を受け取る形に変わる。

### 5. 折れ線は経路結果に載せ、PDFは実線で描く

`Journey` に `originWalkPath` と `destinationWalkPath` を足し、`[経度, 緯度]` の配列で持つ。経路検索の結果から表示、PDF生成の要求まで同じ値を運び、PDFは `walkPaths` として受け取る。描画側の型と `printMapPath` は既存のままでよい。

PDFを別経路で計算し直す案は却下。PDF生成は別プロセスで動き、地図の折れ線が検索結果の徒歩距離と食い違う余地を作る。同じ探索の結果を運ぶ。

線種は、折れ線があるとき実線、ないとき破線とする。実在の経路を破線で描く理由がなくなるためである。破線は、経路の座標を持たない古い要求や、徒歩ネットワークの外にある地点のために残す。

`printed-route-map` の「破線で描く」要求は、この変更で実線へ改める。

### 6. 徒歩ネットワークを読めないときは検索を失敗させる

artifactがない、または形式が不正なときは、経路検索をエラーとして返す。直線距離へ切り替えるフォールバックは作らない。

地点索引（`loadGeocodeIndex`）と同じ扱いにする。フォールバックを残すと、artifactの更新漏れが「静かに精度の低い答えを返す」形で現れ、気づけない。憲章の「旧経路を保つためだけのフォールバックを追加しない」にも反する。

### 7. 目的地目録も同じ判定で作り直す

`scripts/update-destinations.ts` は `selectNearbyStops` を呼んで徒歩圏を判定している。この関数の判定が変わると、目録の候補も変わる。変更と同じ手順で `data/destinations.json` を作り直す。

作り直さないと、目録とルートページの候補が食い違う。実測では106件の場所のうち2件が入れ替わる。

## Risks / Trade-offs

- [artifactが2MB増える] → 1行1要素で差分を読める形にし、gzipでは438KBである。地点索引の1.3MBと同じ扱いにする。
- [OSMの欠落で経路が遠回りになる] → 最大成分への接続を優先し、接続区間を距離に含める。歩道の追加はartifactの更新で追随する。
- [大きな敷地の内側では接続区間が長い] → 接続区間を距離に含め、徒歩時間が実際より短く出ないようにする。
- [階段を含む経路を提示する] → 現行も階段を区別していない。候補の9.3%が階段を含むが、その23%には回避経路がない。データは階段フラグを足せば持てる形にしておき、警告の設計は別の変更に送る。
- [探索の費用が増える] → 2回のダイクストラで17ms、構築は初回61ms。候補の組み合わせごとに探索する実装にはしない。
- [更新を忘れると古い道のままになる] → 地点索引と同じキャッシュとコマンドを使い、更新手順を1つのhow-toにまとめる。ビルドはartifactを読むだけにする。
- [PDFの要求が大きくなる] → 折れ線は500mの徒歩で数十点、数KBに収まる。必要になったら間引く。

## Migration Plan

1. artifactを生成するスクリプトを追加し、`data/walk-network.json` を作る。
2. 徒歩ネットワークの読み込みと探索を追加し、テストで距離と折れ線を固定する。
3. 経路検索の距離の取得元を差し替え、`calculateGridWalkingDistanceKm` を削除する。`NearbyStop.distance` と表示の徒歩時間を分ける。
4. 折れ線を経路結果とPDFへ通し、PDFの線種を実線へ変える。
5. `data/destinations.json` を作り直し、徒歩圏の判定を追随させる。
6. ライセンスページとhow-toを更新し、`npm test`、`npm run lint`、`npm run build` を通す。

切り戻しは、この変更のコミットを戻し、`data/destinations.json` を変更前の内容に戻すだけで完了する。保存形式の移行はない。
