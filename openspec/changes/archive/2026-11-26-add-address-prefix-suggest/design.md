# Design

## Context

`GeocodeSearcher.search` は二つの経路を持つ。数字を含む入力は `findAddress` が街区代表点1件を返し、それ以外は名前索引10,977件を線形に照合する。住所用の正規化 `normalizeAddressQuery` は区名を落とし丁目を数値にするが、名前用の `normalizeSearchTerm` はどちらもしない。そのため `千代田区…` で始まる入力は住所側にも名前側にも掛からない。

索引 `data/geocode-index.json` の街区は1,398件、町は59、丁目を持つ町は31である。丁目を持たない町は28あり、街区数は最多32（神田東松下町）、中央値17。

実測した基準値は次のとおり。

- 索引の読み込みと `GeocodeSearcher` の構築は起動後1回だけ。
- 街区1,398件の索引構築と整列は1.0ms。
- 街区1,398件を二分探索で引くと1,000回で1.6ms。
- 名前索引の線形照合は1回0.3〜0.9ms。

proposal.md - Why の数値と動機はそちらを参照する。

## Goals / Non-Goals

**Goals:**

- 町名・丁目の途中入力で候補を返す。
- 番地の号の扱いを、町の構造から決まる一つの規則にそろえる。
- 索引データの再生成とAPI契約の変更を伴わない。

**Non-Goals:**

- 街区より細かい地番・建物レベルの候補。
- 丁目を持たない町で、数字を打たずに街区を絞り込む手段。街区が最大32あるため、絞り込みは数字の入力に委ねる。
- ひらがな・ローマ字による住所の照合。
- 候補一覧のUI変更。既存の `LocationCandidates` が `name` を表示する。

## Decisions

### 街区索引をソート済みキーとして持ち、接頭辞で引く

町・丁目・街区を `町-丁目-街区` の形にしたキーを1,398件作り、キー順に整列して持つ。照会は正規化した入力の接頭辞で二分探索する。丁目を持たない町のキーは `町-街区` とし、丁目の段を省く。

```
入力 "千代田区神田和泉町1"
  normalizeAddressQuery → "神田和泉町-1"
  parseAddressQuery     → { town: "神田和泉町", chome: 0, block: "1" }
  町の構造              → 丁目なし。1 は街区
  キー照会              → 神田和泉町-1
```

`千代田区霞が関1` は `{ town: "霞が関", chome: 0, block: "1" }` になる。町が丁目を持つので、`block` の値を丁目として読み替え、霞が関一丁目の街区を列挙する。数字の意味を `parseAddressQuery` に決めさせず、町の構造を見て決めるのが要点である。既存の取り違えはこの判定を `parseAddressQuery` の側だけで済ませていたことに由来する。

町名が複数の町に一致するときは住所候補を返さない。名前索引の候補に譲る。`神田` は28町に割れ、`千代田区` は59町すべてに一致するため、ここで住所候補を出すと意味のない一覧になる。

### 代表街区は重心に最も近い街区とする

丁目の候補はその丁目に属する街区の重心を取り、重心に最も近い街区代表点を選ぶ。整列したでたらめな1件目を選ぶと、隣の町の住所を名乗る候補が混じる。

115の町・丁目のまとまりすべてで、選んだ代表点を逆引きすると同じまとまりの住所に戻ることを確認した。重心そのものを座標にすると、区の外や隣町に落ちる場合がある。代表点は必ず索引にある街区の座標を使う。

### 住所候補は駅・公園・公共施設と同じ優先度に置く

住所は「種別」の一種として名前候補と同じ並びに参加させる。優先度を1（駅・公園・公共施設・文化施設・医療機関と同じ）にし、一致の種別を完全一致・前方一致で評価する。並び順は優先度、一致種別、町名の一致、丁目、街区、名前の長さの順で決める。

優先度を最上位にした理由は、住所を打っている利用者に返すべきは住所だからである。試作では次の差が出た。

| 入力 | 住所を優先度2に置く | 住所を優先度1に置く |
|---|---|---|
| 麹町 | 麹町（駅）、麹町警察署、… | 麹町（駅）、千代田区麹町一丁目、二丁目… |
| 隼町 | 隼町（名前）、千代田区隼町1番… | 千代田区隼町1番〜4番、隼町（名前） |
| 霞が関 | 霞が関跡、霞が関ビル内郵便局、… | 千代田区霞が関一丁目…、霞が関跡 |

優先度2では、駅や施設の名前が先に埋まって住所が一覧から落ちる。同じ町名の地点が5件以上ある町では、住所候補が一度も表示されない。

`神田` で駅が先頭に来る要件は、住所候補を出さない規則で守る。住所が候補に入るのは町が一意に決まったときだけであり、その語は町名そのものか、町名の途中である。

### 区名を落とした語でも名前を照合する

名前照合の検索語を、元の語と、先頭の `東京都`・`千代田区` を落とした語の両方で行う。区名を落とすだけだと `千代田区役所` が `役所` になり、部分一致で無関係な候補が混ざる。両方の語で照合すれば、`千代田区役所` は完全一致、`千代田区神田和泉町` は `神田和泉町` との一致になる。

### 数字の解釈を一つの関数に寄せる

`findAddress` と段階的な候補は町の構造から数字の意味を決める同じ判定を使う。`findAddress` は最初の街区だけを代表点として返し、段階的な候補は同じ判定で下位の段階を列挙する。二つの経路が別々の解釈を持つと、`霞が関1-1` と `霞が関1` で違う町を指す事故が起きる。

## Risks / Trade-offs

- [住所候補が名前候補を押し出し、施設名で探す利用者が候補を見失う] → 住所候補を出すのは町が一意に決まったときだけに限る。町名の途中（`千代田区霞`）でも町が一つに決まれば住所を出すが、その語で施設名を探す利用者は少ない。`神田`・`千代田区` のような広い語では住所を出さない。
- [丁目を持たない町で、町名だけでは街区が5件に収まらない] → 神田東松下町は32街区あり、先頭5件だけが並ぶ。数字を打てば絞れる。町名だけで代表1件に絞る案は、利用者が選べない候補を出すことになるため採らない。
- [代表街区が丁目の中心から外れる] → 重心に最も近い街区を選び、115のまとまりすべてで逆引きが同じまとまりに戻ることを確認する。確認はテストに残す。
- [住所候補の追加で `/api/geocode` の応答が変わる] → 応答の形は変えず、`kind` に住所を示す値を加えるだけにする。クライアントは `kind` を並び順にしか使わない。
- [名前索引の照合語が増えて候補の順位が変わる] → 区名を落とした語は、元の語で一致した候補より後ろに置く。既存の並び順の規則は変えない。
- [`隼町4-1` の解釈が変わり、既存の利用者の期待と食い違う] → 現在の `千代田区隼町1番` は誤りである。正しい `千代田区隼町4番` を返す変更を、テストで明示する。

## Migration Plan

1. 仕様の差分を確定し、段階的な候補・番地の号・区名付きの照合のテストを先に書く（RED）。
2. 街区キーの索引と町の構造の判定を実装し、段階的な候補を `search` に組み込む。
3. `findAddress` を同じ判定へ寄せ、号の取り違えを直す。
4. 名前照合に区名を落とした語を加える。
5. テストをGREENにし、索引を再生成せずに全59町で候補が出ることを確認する。

ロールバックは `geocode-search.ts` の差分を戻すだけで済む。索引データとAPI契約を変えないため、データの移行は要らない。
