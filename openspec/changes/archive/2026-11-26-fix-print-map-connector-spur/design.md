# Design

## Context

動機は proposal.md - Why を参照。

現状の折れ線は `src/lib/transit/walk-network.ts` の `walkLeg` が、起点の座標、通過したノードの座標、到着点の座標の順に作る。両端には、地点から最寄りノードまでの接続区間がそのまま直線として入る。距離の計算も同じ2つの接続区間を含む。

PDFの地図は、この折れ線を MapLibre の line レイヤーへ渡し、`printMapPath` が折れ線の有無で実線と破線を切り替える。表示範囲は `printMapBounds` が折れ線の座標だけから求める。

実測した例（麹町出張所を目的地、乗車停留所を麹町出張所停留所にする）では、停留所は最寄りノードまで35メートル、目的地は32メートルで、どちらも同じノード3685に接続する。折れ線は3点になり、目的地から道へ出て同じ道へ戻る。地図の縮尺では「^」形の往復に見える。

## Goals / Non-Goals

**Goals:**

- 地図に描く線を、徒歩ネットワークのノード列だけにする。
- 折れ線が2点に満たない区間でも、地図として読める状態を保つ。
- 徒歩距離・徒歩時間・候補の絞り込みの値を1つも変えない。

**Non-Goals:**

- 建物の入口から道までの実際の通路を描くこと。OSMの歩行ネットワークに建物内の通路はなく、footway の追加はデータ側の作業になる。
- 地点とノードの接続区間を徒歩距離から除くこと。距離は現状の定義を保つ。
- 破線の代わりに点線や半透明の線を引くこと。実在の道でない線を残さない方針をとる。

## Decisions

### 1. 折れ線は道の上のノード列だけにし、接続区間は距離にだけ残す

`walkLeg` が返す折れ線から、先頭の起点座標と末尾の到着点座標を落とす。ノード列（`prepared.snap.node` から `toSnap.node` まで）だけを返す。

接続区間を折れ線から落とす理由は、これが実在の道ではないからである。建物の中の地点から道までの直線は、壁や塀を突き抜けることがあり、地図に引くと歩ける道として読まれる。

距離の定義を変えない理由は、接続区間を除くと、道から離れた地点の徒歩時間が実際より短く出るためである。`route-on-walk-network` の設計で接続区間を含めると決めている。

折れ線の両端に接続区間だけを残す案（ノード列は描き、接続区間は描かない）は却下。折れ線と距離が別の意味を持つようになり、PDF側でもう一度区間を切り分ける必要が生じる。折れ線を「道の上の部分」に限れば、描画側は受け取った線をそのまま描けばよい。

### 2. 地点そのものは地図のマーカーで示し、線では示さない

地図には出発地・停留所・目的地のマーカーを置く。折れ線は道の上で始まり、マーカーは建物の位置に残る。両者の隔たりは接続区間の長さで、おおむね10〜40メートルである。

地点の座標を折れ線へ書き戻す案は却下。往復の「^」がそのまま戻る。

### 3. 表示範囲は折れ線と地点の座標の両方から求める

`printMapBounds` の入力を、折れ線の座標と両端の地点の座標を合わせたものにする。折れ線が1点に縮む区間では、地点の2点だけで範囲が決まる。

折れ線だけから範囲を求める案は却下。折れ線が1点になると範囲が幅0になり、地点のマーカーが地図の外へ出る。地点を加えても、折れ線が地点の外へ張り出す場合は折れ線側が範囲を広げるため、両方を入れる必要がある。

範囲に最小の広がりを持たせる。地点どうしが数メートルしか離れていない場合、そのまま当てると最大縮尺まで寄って道が見えなくなる。中心を保ったまま、東西・南北それぞれ最低200メートルになるよう広げる。200メートルは、街区1つと前後の道が見え、マーカーのアイコンが地図を覆い尽くさない大きさとして選ぶ。

### 4. 折れ線が2点に満たない区間は線を描かない

描画側は、折れ線の長さで線の有無を決める。2点以上なら source と line レイヤーを足して実線を描き、2点未満ならどちらも足さない。破線の描画指定（`PRINT_MAP_FALLBACK_LINE_PAINT`）と、実線と破線を切り替える `followsWalkNetwork` は削除する。

source も足さないのは、GeoJSONの LineString は2点以上を要求するためである。1点以下の LineString を渡すと MapLibre が error を出し、地図の描画失敗としてPDFの生成ごと止まる。

折れ線がない要求に対して破線を描く案は却下。利用者の判断として、実在の道でない線は破線でも残さない。地点のマーカーだけで、どの2地点の地図かは伝わる。

線を引かない区間で地図を省く案も却下。マーカーは、その停留所と目的地がどこにあるかを示す役に立つ。

### 5. マーカーはLucideのアイコンだけにし、図形データからSVGの文字列を組む

マーカーは、停留所を `Bus`、出発地と目的地を `MapPin` の線画アイコンで描く。地名の文字は置かない。停留所は黒地に白、地点は白地に黒と縁取りで塗り分ける。

アイコンの元データは `lucide`（Reactを使わない方の配布物）から取り、その図形データを `renderPrintMapIcon` でSVGの文字列に組んで、`page.evaluate` の引数として渡す。page の中では `innerHTML` で入れる。

`lucide-react` を使う案は却下。`react-dom/server` で静的マークアップにすると、Next のビルドがこの取り込みを React Server Components 向けの解決に変えてしまい、`react-dom/server is not supported in React Server Components.` で `/api/pdf/generate` の収集が止まる。実際に `npm run build` がこの形で失敗した。`react-dom/server.node` を名指ししても、ビルド時の解決では同じ入口へ落ちる。

`lucide-react` のコンポーネントを page の中で使う案も却下。PuppeteerのページにReactの実行環境がなく、動かせない。

SVGのパスを `print-map.ts` に手で書く案は却下。`icon-library-contract.test.ts` が production source の手書きSVG断片（`<path` や `<circle`）を禁じており、アイコンの出所が1つに定まらなくなる。

`lucide` の `createElement` でDOMを組む案も却下。サーバー側に `document` がなく、`document.createElementNS` で落ちる。図形データ（`IconNode`）を読んで文字列に組む。

アイコンの色は `currentColor` のまま出し、マーカーの文字色で塗り分ける。SVGに色を焼き込むと、黒地用と白地用で2種類のマークアップを持つことになる。

アイコンの一辺は16ピクセルにする。憲章が利用者向け文字に求める16ピクセルと同じ値で、地図の中の記号として小さすぎず、地名の文字を外した分をアイコンの形で受け止められる大きさである。

マーカーの位置合わせは `anchor: "center"` にする。MapLibreはマーカーの `transform` を `anchor` から組み立てて要素のインラインスタイルへ書き込むため、`PRINT_MAP_CSS` に置いている `translate(-50%, -100%)` は効いていない。この指定を消し、位置合わせは `anchor` だけで決める。

地点のマーカーは停留所のマーカーより先に置く。両者が重なる区間でも、後に置いた停留所のバスが上に残る。

### 6. 折れ線の有無でPDF本文を変えない

`walkPaths` は任意の項目のままにする。折れ線がなくても地図は出し、経路・時刻・乗換・メモの内容は変えない。既存の契約テスト（`pdf-route-contract.test.ts`、`pdf-print-map-html.test.ts`）が確かめている性質をそのまま保つ。

## Risks / Trade-offs

- [折れ線が1点になる区間が増える] → 同じノードに接続する2地点では、線が消えてマーカー2つだけの地図になる。徒歩が建物の中だけの区間なので、道を描かないことは事実に合う。
- [地名を消すと、どの停留所か読めなくなる] → 停留所名は経路本文と地図の読み上げ名に残る。地図だけを切り取って見せる場面では、アイコンの種類と位置から読み取ることになる。
- [Lucideの配布物が2つになる] → `lucide-react` は画面のアイコン、`lucide` はPDFのアイコンで使う。`lucide` は図形データだけの配布物で、Reactを要求しない。
- [地図から徒歩の向きが読みにくくなる] → 折れ線の始点と終点は道の上で、マーカーは建物の位置にある。マーカーと線の対応は距離で読み取る。向きは経路本文の停留所名と時刻で示す。
- [最小の広がりで地図が粗くなる] → 200メートル四方は、徒歩区間が数十メートルのときに街区の位置関係を示す大きさである。これより細かい道の形は、この地図の用途では要らない。
- [接続区間を含む距離と、描く線の長さが食い違う] → 紙面の地図は経路の形を示すもので、距離の根拠ではない。徒歩時間は本文の値を使う。

## Migration Plan

1. 折れ線の作り方を変え、徒歩距離が変わらないことをテストで固定する。
2. 描画側から破線を削除し、線の有無と表示範囲の求め方を変える。
3. `lucide`を依存へ加え、マーカーをLucideの図形から組んだSVGへ置き換える。
4. PDFの契約テストを新しい線種とマーカーへ合わせ、`npm test`、`npm run lint`、`npm run build` を通す。

切り戻しは、この変更のコミットを戻すだけで完了する。保存形式とartifactの移行はない。
