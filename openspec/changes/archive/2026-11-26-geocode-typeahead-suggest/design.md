# Design

## Context

現状の住所検索は、フォームのsubmit（Enterまたは虫眼鏡ボタン）で1回だけ `/api/geocode` を呼ぶ。検索語は `useGeocodingSearch` が保持し、候補は `LocationCandidates` がボタンの一覧として描画する。候補を押すと地点が確定し、`LocationFieldset` がfieldset全体を確定表示に切り替える。

実測した制約は次のとおり。

- 索引の検索は1回0.3〜0.9ms、索引の構築は11.6msでプロセス起動後に1回だけ。候補5件の応答は673バイト。
- `GeocodeSearcher.search` は約11,000件の名前を線形に走査する。1,000回で445ms。打鍵ごとに呼んでも1リクエスト1ms未満。
- 地点検索・経路検索・PDF生成・結果ページは同じレート制限バケツ（IPあたり1時間600回）を共有し、1リクエストごとにSQLiteへ2読み1書きする。
- クライアントは429を受けると入力途中の文字を捨てて `/rate-limit?source=home` へ遷移する。
- `InputField` は `autoComplete="true"` を固定で設定している（無効値のためブラウザは無視する）。

詳細な動機は proposal.md - Why を参照。

## Goals / Non-Goals

**Goals:**

- 打鍵に応じた候補表示を、既存の候補一覧コンポーネントと確定フローを保ったまま追加する。
- 地点検索を利用回数の制限から外し、入力中に429で画面遷移しないようにする。
- 入力中の検索が支援技術のユーザーにノイズを与えないようにする。

**Non-Goals:**

- ARIA combobox＋activedescendant による候補の矢印キー操作。候補は既存どおりボタンの一覧とし、Tabで移動する。
- 地点検索をブラウザ内で行うための索引のクライアント配信。索引は1.3MB（gzip 260KB）あり、打鍵ごとの通信1msに対して配信量が見合わない。
- 経路検索・PDF生成・結果ページの利用制限の変更。
- ひらがな・ローマ字による検索の拡充。

## Decisions

### 検索の起動はフックに寄せ、入力値をフックが持つ

現在は各Selectorが `useState` で入力値を持ち、フックは検索だけを担う。打鍵に応じた検索は入力値の変化を見る必要があるため、入力値と候補の状態を `useGeocodingSearch` に集約し、Selectorは返り値の `query` / `setQuery` をバインドするだけにする。入力のデバウンス・IME判定・古い応答の破棄が1か所に収まり、目的地と出発地で同じ挙動になる。

### 打鍵から250msの静止で検索し、変換中は送らない

デバウンスは250ms。人の打鍵間隔（日本語入力で1秒に3〜5文字）では、静止してから1回だけ送られる。

```
keydown  --> [composition中?] --yes--> 何もしない（変換確定まで待つ）
                    |
                    no
                    v
             250msのタイマーを張り直す
                    |
              （静止）
                    v
             直前の検索を世代番号で無効化 -> fetch -> 候補を差し替え
```

IMEの判定は `compositionstart` / `compositionend` のイベントで持つ。`isComposing` フラグをキーイベントから読むだけでは、SafariとFirefoxで `compositionend` 後に発火する `input` の扱いが揃わないため、イベントで状態を持つ。日本語入力では「か」→「かん」→「かんだ」の未確定文字列が索引の名前と部分一致して誤った候補を出し、変換確定ごとに通信が3倍になる。これを避けるのが主目的。

デバウンスを300msより長くする案は却下。候補が出るまでの体感が遅れ、打ち終わってから候補が出るのでは決定ボタンを押すのと変わらない。

### 古い応答は世代番号で捨てる

`AbortController` ではなく、フックが持つ世代番号で判定する。応答が届いた時点で世代が最新でなければ、状態を更新しない。

`AbortController` を採る案も検討したが、中断してもサーバー側の探索は0.5msで終わっており、通信の節約効果がほぼない。一方で `searchGeocoding` のシグネチャに `AbortSignal` を足すと、既存の呼び出し（GPSの逆引き、テストのfetcher注入）に波及する。表示の正しさに必要なのは「最後に始めた検索の結果だけを表示する」ことで、世代番号で足りる。

### 入力中の失敗は黙り、確定を試みたときだけ伝える

検索の状態を「入力中」と「確定」の2つに分ける。

| 契機 | 候補なし | 通信失敗 |
|---|---|---|
| 打鍵（デバウンス後） | 何も出さない | 何も出さない |
| 入力欄からフォーカスを外す | エラーを示す | エラーを示す |
| Enter / フォーム送信 | エラーを示す | エラーを示す |

`role="alert"` と `aria-invalid` は確定の契機だけで立てる。打鍵のたびに「一致する地点が見つかりませんでした」を読み上げさせると、支援技術のユーザーは入力の途中で何度も通知を遮られる。2文字未満では検索自体を行わないため、1文字目で空振りすることもない。

### Enterはデバウンスを待たずに検索する

フォーム送信は既存どおり残し、送信時は保留中のタイマーを取り消して即座に検索する。候補表示のために待たされた結果を、確定の操作でもう一度待つのは無駄である。

### 住所欄から虫眼鏡ボタンを外す

候補が自動で出るため、submit専用のボタンは役目を失う。`SearchButton` は住所欄から外し、用途がなくなれば削除する。最終経路検索の可視文字ボタン（`search-route`）はそのまま残す。

`search-controls` 仕様の「住所検索ボタンは虫眼鏡アイコンのみ」は成立しなくなるため、要件を差し替える。

### 候補はボタンの一覧のままにする

ARIA combobox のパターン（`aria-activedescendant`、矢印キー、Escでの閉じ）は、実装が繊細で、キーボードやスイッチで操作する利用者には roving focus が仇になることがある。既存の候補はフォーカス可能なボタンで、Tabで移動し、EnterかSpaceで確定できる。この形を保ち、次の2点だけ足す。

- 入力欄の `aria-controls` に候補一覧のidを指定し、候補との関係を示す。
- 検索が落ち着いて候補が出たときだけ、件数を `role="status"` の1行で知らせる。打鍵のたびには出さない。

候補一覧は最大5件で、`LocationCandidates` の各項目は44 CSS px以上の操作領域と可視フォーカスを持つ。Tabで候補を通り抜ける負担を減らすため、Escで候補を閉じられるようにする。

### 入力欄の自動補完を切る

`InputField` の `autoComplete="true"` を、住所欄では `off` にする。ブラウザの履歴候補と地点索引の候補が同じ位置に重なると、どちらを操作しているのか分からなくなる。`InputField` は `autoComplete` を受け取れるようにし、既定は現状を保って住所欄だけ `off` を渡す。

### 地点検索の利用制限だけを外す

`/api/geocode` から `appRouterRateLimitMiddleware` の呼び出しを外す。地点検索と逆引きはプロセス内の索引しか読まず、守るべき外部資源も共有バケツも持たない。DBへの2読み1書きも消え、入力中の検索がSQLiteの状態に依存しなくなる。

バケツを `ip` ではなく種別ごとに分ける案（`rate_limits` の主キーを複合にする）も検討したが、地点検索に残す理由がない。上限を上げるだけの案は、上限に達したときに利用制限画面へ飛ぶ挙動が残るため採らない。

`checkRateLimit`、`appRouterRateLimitMiddleware`、`apiRateLimitMiddleware`、`withRateLimit`、`rate_limits` テーブル、`/rate-limit` 画面は、経路検索・PDF生成・結果ページが使い続けるため残す。`apiRateLimitMiddleware` と `withRateLimit` は Pages Router 用で現在の呼び出し元がないが、この変更の範囲外とする。

### クライアントから429の分岐を消す

`GeocodingStatus` から `rate-limited` を、結果型から `isRateLimited` を除く。`useGeocodingSearch` と `OriginSelector` の逆引きから利用制限画面への遷移を削り、`useRouter` の依存も落とす。`place_search` の `outcome` は `found` / `not_found` / `failed` の3つになる。

## Risks / Trade-offs

- [打鍵ごとの検索でサーバーのCPUを使い切られる] → 1リクエスト0.5msで、索引はプロセス内にある。悪用が観測された場合は、Cloudflareのレート制限ルールでエッジに置く。`x-forwarded-for` の先頭を信じる現行の判定より、エッジのほうが確実に抑えられる。
- [候補一覧がフォーカスを奪い、キーボードのTab移動が増える] → 最大5件に抑え、Escで閉じられるようにする。候補は入力欄の直後に置き、DOM順と視覚順を一致させる。
- [変換確定直後に古い読みの検索が走る] → `compositionend` のあとに発火する `input` で新しい値からタイマーを張り直す。世代番号により、変換中の検索結果が確定後の候補を上書きしない。
- [ブラウザの自動補完を切ることで、以前の入力を再利用できなくなる] → 索引の候補が同じ役割を果たす。履歴の再利用より、地点索引に存在する名前だけが出るほうが誤確定が少ない。
- [429の分岐を消したことで、ほかのAPIの429が地点検索のエラーとして表示される] → 地点検索のクライアントは `/api/geocode` しか呼ばない。経路検索とPDFは別の呼び出し経路で、既存の扱いを変えない。
- [進行中の analytics-usage-measurement と `place_search` の定義が食い違う] → アーカイブ前に `outcome` から `rate_limited` を除く。この変更のタスクに含める。

## Migration Plan

1. 仕様の差分を確定し、テストを先に書く（RED）。
2. `/api/geocode` からレート制限を外し、サーバー側の429応答と `limitExceeded` を消す。
3. `geocoding-search` とフックから `rate-limited` を消し、Selectorの遷移を削る。
4. フックに入力値・デバウンス・IME・世代番号を実装する。テストをGREENにする。
5. `InputField` に `autoComplete` を足し、住所欄を `off` にする。
6. 住所欄の `SearchButton` を削除し、`page.test.tsx` などのボタン契約を差し替える。
7. 仕様の `search-controls` と `location-search` をアーカイブ時に反映する。

ロールバックは地点検索のクライアント差分とAPIの差分を戻すだけで済む。利用制限のバケツと `/rate-limit` 画面は残しているため、経路検索側の巻き添えはない。
