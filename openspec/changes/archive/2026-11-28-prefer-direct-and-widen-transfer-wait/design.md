# Design

## Context

動機は proposal.md の Why を参照。現状は次のとおりである。

| 箇所 | 現在の挙動 |
|---|---|
| 乗換待ちの上限 | `ROUTE_PARAMS.MAX_TRANSFER_WAIT = 15`（分）。これを超える乗り継ぎは候補にしない |
| 徒歩優先の比較 | 到着秒＋`TRANSFER_PENALTY_MINUTES`（10分）×乗換回数。到着時刻指定では出発秒から引く |
| はやさ優先 | 到着時刻（到着時刻指定では出発時刻）だけ |

平日の時刻表（停留所79、便91、stop_times 1,091）で測った値は次のとおり。

| 待ち上限 | 経路なしになる停留所の組（5,112組中、平日10時） |
|---|---|
| 15分 | 1,820 |
| 30分 | 288 |
| 45分 | 0 |
| 60分 | 0 |

画面と同じ近隣停留所の組み合わせ（各5件）でも、待ち上限15分では10時に56組、12時に57組、15時に73組が経路なしになり、上限25〜45分で0組になる。乗り継ぎ待ちの実測は中央値40分、15分以内は24%である。待ち上限を15分にした根拠は、2025年4月のパラメータ整理（`2f84ee8`）で値を1箇所に集めたときに引き継がれたものだった。

選択規則については、ブラウザ相当の組み合わせ（1,542組）で比較した。

| 規則 | 現在の規則からの選択変更 |
|---|---|
| 直通優先→到着→徒歩 | 46 |
| 到着→直通→徒歩 | 2 |
| 徒歩→直通→到着 | 1,394 |
| 直通優先→徒歩→到着 | 1,263 |

## Goals / Non-Goals

**Goals:**

- 乗り換えれば行ける組を、経路なしとして表示しない。
- 乗換の手間を分単位のコストとして足し引きするのをやめ、一本で着く直通を既定にする。

**Non-Goals:**

- 待ち時間の表示。結果画面の変更は今回の範囲外とする。
- 乗換回数の上限（1回）の見直し。
- 異なる停留所へ歩く乗換の探索。
- はやさ優先の規則の変更。

## Decisions

### 1. 乗換待ちの上限を60分にする

`ROUTE_PARAMS.MAX_TRANSFER_WAIT` を15から60へ変える。平日10時の停留所の組で、上限45分は0組、上限60分も0組で、差は出ない。45分で足りる時間帯でも、16時は45分で1,176組、60分で1,050組が残るので、60分を採る。

上限60分でも、`MAX_TRANSFER_CANDIDATES`（10件）が結果を削ることはない。上限60分で79停留所×8組を調べ、候補数の上限を10件と40件で比べて差分は0件だった。探索の費用も、200問で上限15分が43ms、上限60分が32msで、差はない。

最小待ち1分は変えない。0分にすると同一時刻の乗り継ぎを拾い、平日10時の経路なしは1,098組まで減るが、乗り継ぎの余裕を0にする根拠がない。実測でも待ち0分の乗り継ぎは188件あり、時刻表の丸めで発生している。1分を下限として残す。

### 2. 徒歩優先は「直通優先と30分の閾値」にする

徒歩優先の比較から `TRANSFER_PENALTY_MINUTES` をなくす。規則は次のとおり。

- 出発時刻指定: 候補に直通があれば直通を既定とする。乗換は、到着が直通より1,800秒以上早い場合に限り選ぶ。
- 到着時刻指定: 直通を既定とする。乗換は、出発が直通より1,800秒以上遅い場合に限り選ぶ。
- 直通がないときは乗換を選ぶ。
- 同じ種類どうしでは、到着（到着時刻指定では出発）の早い方、同じなら徒歩距離、次に出発の早い方を選ぶ。

30分は、直通を常に優先したときの遅れから決めた。平日の4時点（8時・10時・12時・15時）で、直通と乗換の両方がある4,497組のうち101組が直通優先で遅れ、中央値14分、90パーセンタイル50分、最大70分だった。30分の閾値なら、この遅れは29分以内に収まる。

閾値を「直通優先→到着→徒歩」の順序だけにすると46組で選択が変わり、その大半は乗換の方が5〜29分早い組である。提示された経路の到着が遅れる方向なので、閾値を置く。

「10分以上早いときだけ乗換」は、現在の10分コストと選択が一致する（平日4時点・20,384組で完全一致）。乗換の待ち上限を直すだけでは、乗換の方が早いのに直通を選ぶ組が最大70分遅れたまま残る。

### 3. 比較の入力を単純にする

`route-result-ranking.ts` は、加算した主値を持つ比較用の鍵を作る形をやめ、次の順で比べる。

1. 直通か乗換か（直通を先）
2. 到着（出発時刻指定）または出発（到着時刻指定）
3. 総徒歩距離
4. 出発（出発時刻指定）または到着（到着時刻指定）

はやさ優先は1を飛ばし、2から比べる。`TRANSFER_PENALTY_MINUTES` と `ROUTE_PARAMS` からの再輸出は消す。`route-algorithm.test.ts` の「乗換1回のコストを10分として探索パラメータに置く」は、待ち上限60分を確かめるテストへ置き換える。

## Risks / Trade-offs

- [乗換が11〜29分しか早くない組が直通になる] → 直通を既定にした結果であり、遅れは最大29分。徒歩優先の意図に沿う。はやさ優先では今までどおり乗換を選ぶ。
- [乗換待ちが最大60分になる] → 上限を広げた結果として、長時間の待ちを含む経路が返る。待ち時間は結果画面の乗換の前後の時刻として読める。表示の追加は今回行わない。
- [待ち上限15分を前提にした既存テストが落ちる] → 待ち16分以上の乗り継ぎを候補にするテストへ書き換える。REDを確認してから実装する。

## Migration Plan

- データの移行はない。保存済みの結果URLは再検索すると新しい規則で評価される。
- 切り戻しは `MAX_TRANSFER_WAIT` を15へ戻し、比較を10分コストへ戻すこと。両者は独立した変更なので、片方ずつ戻せる。
