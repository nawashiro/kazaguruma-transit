# Design

## Context

動機は proposal.md の Why を参照。現状は次の3点である。

| 箇所 | 現在の挙動 |
|---|---|
| 通常経路 | 探索結果の先頭 `routes[0]` をそのまま返す。優先条件を読み取らない |
| 周辺停留所の探索 | `selectBestRouteCandidate` を通すが、比べる値は総徒歩距離と総所要時間だけ |
| 探索結果の並び | 到着時刻の昇順。徒歩距離は候補間で同じことが多い |

乗換は同一停留所の乗り継ぎだけを生成する（`destinationBoardingsByStop` を降車停留所IDで引く）。実測4,073件の乗換候補は全件が同一停留所で、乗換徒歩は0である。待ち時間は中央値10分、90パーセンタイル10分、最大15分。

徒歩距離の二重計上は次の実測による。出発地と乗車停留所が同じノードへ接続する場合、`walkLeg` は両端の接続区間を足す。

| 地点 | 直線距離 | 現行の徒歩距離 |
|---|---|---|
| 東日本銀行神田支店の施設座標から同バス停 | 3.4m | 64.4m |
| 千代田区役所の施設座標から同バス停 | 8.1m | 21.4m |
| 停留所自身の座標から同じ停留所（79停留所の最大） | 0m | 87.7m |

この値は `Math.ceil` で徒歩分になり、探索時刻を押し上げる。東日本銀行神田支店10時28分の入力では徒歩2分を足して10時30分以降を探し、10時29分発の内神田ルートを取りこぼす。

## Goals / Non-Goals

**Goals:**

- 優先条件を、通常経路と周辺停留所の両方で同じ規則として適用する。
- 乗換の手間を、比較できるコストとして明示する。
- 徒歩距離の二重計上を止め、境界時刻の取りこぼしを消す。

**Non-Goals:**

- 異なる停留所へ歩く乗換の探索。コミュニティバスの利用実態に照らして作らない。将来作る場合は、乗換の徒歩距離を実測してコストへ入れ直す。
- 乗換の待ち時間をコストとして別に数えること。待ちは到着時刻に既に現れ、乗換コスト10分がその代表値として働く。
- 候補の生成範囲の拡大。探索が見つけた候補だけを並べ替える。

## Decisions

### 1. 比較の値を「到着秒＋乗換コスト」に統一し、同値時の順序を固定する

比較の主値は、出発時刻指定では `arrivalSeconds + TRANSFER_PENALTY_MINUTES × 60 × transfers`、到着時刻指定では `departureSeconds - TRANSFER_PENALTY_MINUTES × 60 × transfers` とする。出発時刻指定では小さい方、到着時刻指定では大きい方を選ぶ。

同値時の順序は、総徒歩距離、乗換回数、時刻の順とする。時刻は出発時刻指定なら出発の早い方、到着時刻指定なら到着の早い方とする。

総所要時間で比べる案は却下。総所要時間は探索の窓の中で待ち時間を含むため、遅い便を長く待つ候補が不利になり、比較の意味が安定しない。到着時刻は利用者が実際に受け取る値である。

既存の `selectBestRouteCandidate` の引数（`prioritizeSpeed: boolean`）は残さず、`{ prioritizeSpeed, isDeparture }` の対象へ変える。呼び出し元は2箇所だけで、どちらも `isDeparture` を持っている。

### 2. 乗換コストは10分とし、`ROUTE_PARAMS` に置く

実測で、乗換コストごとの選択の変化は次のとおりである。

| コスト | 東日本銀行神田支店→千代田区役所の乗換選択 | 全4,660組の選択変更 | 到着の最大遅れ |
|---|---|---|---|
| 0分 | 6/114 | 0 | 0分 |
| 5分 | 6/114 | 103 | 0分 |
| 10分 | 0/114 | 103 | 0分（12時・15時基準では最大7〜10分） |
| 15分 | 0/114 | 107 | 最大10分 |

10分は、ご指摘の経路を直通へ変え、かつ到着の遅れをほぼ生まない上限である。乗換の待ち時間の中央値も10分で、利用者が乗換に払う手間の代表値として説明できる。5分では対象の経路が乗換のまま残る。15分では到着の遅れが増える。

値は `ROUTE_PARAMS.TRANSFER_PENALTY_MINUTES` に置く。探索の窓（`MIN_TRANSFER_WAIT`・`MAX_TRANSFER_WAIT`）と同じ場所に集め、探索の制約と選択の重みを1箇所で読めるようにする。

### 3. 通常経路でも探索結果の全候補を比較する

`findConventionalRoute` は `routes[0]` を返している。これを、`routes` の全候補に同じ徒歩距離（停留所1組なので共通）と経路ごとの到着・出発時刻・乗換回数を与え、選択規則へ渡す形に変える。

`routes[0]` を残して乗換コストだけを足す案は却下。先頭が乗換である場合、比較の相手がいないためコストが効かない。

候補ごとの徒歩距離は停留所1組では同じ値になる。それでも比較の入力として渡すのは、周辺停留所の探索と同じ関数を使い、規則を1つに保つためである。

### 4. 乗換の徒歩距離0に根拠を付ける

`convertTimeTableRouteToJourney` の `distanceMeters: 0` は「後で修正」のまま残っている。乗換が同一停留所に限られる現状では0が正しい。コメントを根拠の記述へ変え、`TransferInfo` の `distanceMeters` を使わない側に寄せる。

異なる停留所への乗換を将来足すときは、`route-algorithm` の索引を降車停留所から近隣停留所へ広げ、この0を実測値へ変える必要がある。この制約を design.md に残し、コードには「同一停留所の乗り継ぎだけを生成する」という現在の性質だけを書く。

### 5. 同じノードへ接続するときは直線距離にする

`walkLeg` で `prepared.snap.node === toSnap.node` のとき、`distanceKm` を2点間のハバーサイン距離にする。折れ線は現状どおりそのノード1点を返す。

接続区間を片方だけにする案（`Math.max(prepared.snap.km, toSnap.km)`）は却下。同じノードへ向かう2点は、ノードを経由せず直接歩ける。片方の接続区間を残すと、ノードから遠い方の点の距離だけが残り、直線距離より長い値になる。

この変更は `walk-network` の MODIFIED 要件と、既存テスト「同じノードに接続しても徒歩距離は両端の接続区間を含む」の書き換えを伴う。既存テストは現在の挙動を固定しているため、RED から作り直す。

#### 500メートル判定の境界を動かさない

この補正で短くなるのは、地点と停留所が同じノードへ吸着する場合だけである。実測では、地点索引の106地点のうち距離が変わるのは6地点で、いずれも最も近い停留所までの距離が17〜67mであり、500mの境界からは遠い。境界付近（450〜650m）にある6地点の距離は1mも変わらない。

したがってこの補正だけでは `data/destinations.json` は変わらない。境界を動かさない根拠として、次の2つを実装の制約にする。

- 補正は `walkLeg` の中だけで行い、500メートル判定を行う `selectNearbyStops` と `findConventionalRoute` の上限比較には手を入れない。両者は `walkLeg` の返す距離をそのまま使う。
- 補正後の距離は補正前以下になる。同ノードのときは `haversineKm ≤ prepared.snap.km + toSnap.km` が常に成り立つため、判定は「外から中へ」にだけ動きうる。実測ではその移動も0件である。

`npm run update-destinations` の結果に差分が出たときは、この想定が崩れたことを意味する。その場合は差分を機械的に受け入れず、どの地点が境界をまたいだかを確認してから作り直す。tasks.md の 5.2 にこの条件を書く。

### 6. 結果画面の+5分を削除する

`IntegratedRouteDisplay` の `walkMinutes` は `walkingTimeMinutes + 5` を返す。この5分は、徒歩時間を直線距離から概算していた頃の不正確さを吸収するために置かれていた。現在は徒歩ネットワークの距離から求めており、根拠がない。

+5分を残して徒歩時間の側を調整する案は却下。表示だけの補正を経路検索の値へ混ぜると、探索時刻と表示時刻が再び食い違う。

`walkingTimeMinutes` が無いときは0を返す現在の分岐は残す。表示は乗降時刻のままになる。

## Risks / Trade-offs

- [到着が遅くなる経路が返る] → 徒歩優先の意図どおりだが、利用者が遅れに気づかないと不満になる。画面の表示は既存のままで、到着時刻は常に表示される。実測の最大遅れは10分。
- [通常経路の候補数が増える] → `routes` は最大でも数十件で、比較は定数時間である。探索の費用は変わらない。
- [同ノード補正で500メートル判定が変わる] → 実測では106地点のうち6地点の距離が短くなるだけで、500m境界の帯（450〜650m）にある6地点は変わらない。補正を `walkLeg` の中だけに閉じ、判定側の比較には触れない。`npm run update-destinations` に差分が出たら想定が崩れているため、境界をまたいだ地点を確認してから作り直す。
- [到着時刻指定の比較を反転し忘れる] → 到着時刻指定で `arrivalSeconds + コスト` を使うと、遅く出発する便が不利になる。設計では `isDeparture` で式ごと切り替え、両方のテストを置く。

## Migration Plan

- データの移行はない。保存済みの結果URLは再検索すると新しい規則で評価される。
- 目的地目録は `npm run update-destinations` の結果が変わったときだけ作り直す。差分が無ければ触らない。
- 切り戻しは `TRANSFER_PENALTY_MINUTES` を0にすることで、選択規則の適用だけを残して乗換コストを無効にできる。ただし通常経路の全候補比較は残る。
