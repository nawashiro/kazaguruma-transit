# Design

## Context

動機と範囲はproposal.mdに記載する。入力、検索結果、共有検索ボタンをまたぐ変更であり、結果取得と利用制限の実行場所も変わるため、この設計を作成する。

調査時点の構成は次のとおり。

- `src/app/page.tsx`は施設データをサーバーで読み、`HomeRouteForm`へ渡す。入力項目の出し替え、日時、優先条件、最終遷移はクライアントで扱う。
- 住所の2つのセレクターはそれぞれformを持つ。`useGeocodingSearch`と`searchGeocoding`は千代田区の補完と先頭結果の採用を担い、`/api/geocode`がGoogleへ問い合わせる。
- `DateTimeSelector`は端末日時を初期値とし、出発・到着に応じてラベルと説明を変更する。優先条件の保存キーは`prioritizeSpeed`である。
- `LocationSuggestions`だけが`CategoryTabs`を使う。`ResetButton`も入力画面だけで使われている。施設一覧は条件付きのtabpanel、ピンアイコン、truncate、高さ制限と内部スクロールを持つ。
- `/routes`はクライアントページで、`RouteSearchResults`が`/api/transit`を取得する。経路表示のほかにNostrメモ、掲示板、PDF・カレンダーの操作を同じコンポーネントで組み立てている。
- 経路APIのGET・POSTは共通の利用制限を通り、`TransitService.process`を呼ぶ。`parseRouteSearchParams`と`createRouteResultViewModel`は表示から独立している。
- サイト内で検索を実行するボタンは、調査時点では住所検索2か所と最終経路検索である。施設ページへのリンクは検索実行ボタンではない。
- DaisyUIのローカルCSSではfieldsetの文字サイズが`.75rem`である。グローバルCSSの16px指定だけではlegend・labelなどの継承サイズを保証できない。

## Goals / Non-Goals

**Goals:**

- HTMLのフォーム送信、ラベル、グループ化を基本とし、入力操作のためのJSを必要な範囲で利用する。
- 結果本文とブラウザ機能を分け、既存URLと利用制限を保ったままサーバーで経路を描画する。
- DOMの意味構造、アクセシブルな名前、リフローを実際の表示と操作で検証できる構成にする。

**Non-Goals:**

- JS無効時の全面対応やJS使用量の数値目標を設けない。GPS・住所検索・端末日時・localStorageを無理にサーバーへ移さない。
- 経路の選定アルゴリズム、歩行速度、住所候補の選び方を変更しない。
- 新しいフォームフレームワークやUIライブラリーを導入しない。共通Buttonとルビ切替ボタンのコントラスト修正を除き、共通テーマやサイト全体のカードを再設計しない。

## Decisions

### 1. 住所検索と最終検索は別フォームにする

画面は「目的地」「出発地」「日時」「優先条件」の順に常時表示する。目的地内では名前検索formを施設一覧より前に置き、DOM順・表示順・Tab順をそろえる。CSSの並べ替えだけで対応しない。目的地と出発地には、それぞれのfieldset内に独立した住所検索formを置く。最後のGET formは日時・優先条件のグループ、確定座標のhidden入力、最終submitを持ち、`action="/routes"`とする。住所のsectionと最終formは兄弟要素とし、フォームの入れ子を作らない。

住所検索formは既存のJSによる非同期検索を継続する。最終formは`origin`、`destination`、`time`、`isDeparture`、`prioritizeSpeed`の名前と既存形式の値を送る。日時と各ラジオに安定したname / valueを付け、正しい条件ならブラウザの通常のGET送信で遷移する。未確定地点は送信時に検証し、項目に関連付いたエラーを表示して送信を止める。日時のrequiredなど標準の検証も使う。

全項目を1つのformで囲み、住所検索をすべてクリックハンドラーにする案は採用しない。住所欄でのEnterと最終検索を区別しにくく、ほかの必須項目が住所検索を妨げるためである。フォーム外部関連付けを広範囲に使う必要もない。

### 2. 住所の確定はグループ内の状態にする

各地点は編集中または確定済みの状態を持つ。確定後は同じfieldset内で住所表示と「なおす」に置き換える。「なおす」とGPSボタンは内容に応じた幅とし、fullWidth、w-full、flex伸長や親のstretchで全幅にしない。44 CSS px以上の操作領域を保ち、狭い幅ではラベルを折り返す。再編集は対象だけを編集中へ戻し、以前の確定座標を最終送信対象から外す。ほかの地点、日時、優先条件は保持する。

既存の千代田区補完、先頭結果の自動採用、GPS座標と任意の住所逆引き、429の案内を維持する。GPS操作は住所検索を送信しない`type="button"`とし、表示名を「端末のGPSを許可する」にする。目的地ディープリンクは既存形式を受け取り、4グループを隠さず確定状態へ反映する。

住所検索中の通知・エラーだけを必要に応じて読み上げる。フォーム全体をaria-liveで囲む方式はやめる。再編集で表示が入れ替わる場合は対象入力へフォーカスを移し、確定操作のあともフォーカスを失わせない。

### 3. 日時と端末設定はクライアント側に残す

`DateTimeSelector`は端末の現在日時を一度設定する。ラベルは「日時」で固定し、出発時刻・到着時刻は通常のラジオボタンにする。入力値が空になっただけで現在日時を再注入せず、標準の必須検証に任せる。

優先条件は既存キー`prioritizeSpeed`の文字列true / falseを引き続き使用する。未保存時はfalse、ラベルは仕様にある2つの文言とする。選択をlocalStorageへ保存し、最終GETには選択値を明示する。保存領域が使えない場合も画面上の選択と送信は利用できる構成にする。サーバー日時、Cookieへの保存先変更、歩行速度の変更は行わない。

### 4. カテゴリは標準の折りたたみとリストを使う

カテゴリごとにdetails / summaryを縦に配置し、内部にul / liと施設選択ボタンを置く。独自のtablist、tabpanel、矢印キー制御、開閉アニメーション、カテゴリ用のARIAを引き継がない。ピンアイコンとtruncateを除き、長い文字列が折り返す幅を確保する。max-heightとoverflowによる一覧内部のスクロールも除く。

軽微な既定案として、初期状態はすべて閉じ、複数カテゴリを同時に開ける。排他的な開閉制御は加えない。全施設の常時展開より縦の長さを抑えつつ、折り返すタブ案より独自操作を減らせる。

### 5. 検索ボタンとARIAを用途で整理する

住所検索2か所は既存Buttonを使うSearchButtonで共有し、Searchアイコンのみ、`aria-label="検索"`、アイコンは`aria-hidden="true"`とする。最終submitは通常のButtonで可視文字「経路を検索」を表示し、可視ラベルをアクセシブルな名前に使う。住所検索のアイコン専用表現を最終検索へ流用しない。いずれも44 CSS px以上の操作領域を確保する。

GPS、日時、優先条件は可視ラベルを名前として使い、同じ意味を上書きするaria-labelを外す。legendの標準意味論で表現できるrole / aria-labelledbyは重ねない。入力エラーのaria-invalid / aria-describedbyや必要な状態通知は維持する。ARIAの一括削除や、GPSなど検索以外のボタンのアイコン化は行わない。

### 6. 結果ページはサーバー取得と静的本文を持つ

`src/app/routes/page.tsx`を非同期のServer Componentにし、Next.js 15のsearchParamsから既存パーサーで条件を検証する。サーバー専用の取得処理を通して`TransitService.process`を呼び、`createRouteResultViewModel`で表示用データを作る。自サイトのAPIをサーバーからHTTPで呼び直す構成は取らない。

`IntegratedRouteDisplay`は不要なクライアント宣言とCard依存を除き、停留所・時刻・乗換をDaisyUIのスタイルと見出し、リスト、区切り線で描画する。各乗車区間のDOM順と表示順は乗車停留所・路線名・降車停留所とし、乗換でも区間ごとにこの対応を保つ。路線名と停留所名は同じ算出フォントサイズで16px以上とし、路線名だけを見出しサイズにしない。ページのh1で目的が伝わるため、重複する「経路」見出しは置かない。`StopTimeDisplay`などサーバーで動く表示はそのまま利用する。読み込み中表示が必要ならサーバー側のSuspenseを使い、本文の表示をクライアントのeffectに戻さない。

Nostr、メモ取得、PDF・カレンダー操作は小さなクライアント側コンポーネントへ分離し、シリアライズ可能な経路データを渡す。PDF用memoDataはその範囲で管理する。Nostrの初期化・失敗でサーバー描画済み本文を置き換えない。掲示板の無効設定ではNostr取得を始めない。

### 7. 利用制限とAPI契約を共有して維持する

既存利用制限のIP単位の判定・加算部分を、NextResponseに依存しないサーバー専用処理として抽出する。APIは従来のミドルウェアをアダプターとして維持し、結果ページはリクエストヘッダーから同じIP識別規則を使って判定する。判定の失敗を含め、現在の制限方針は変えない。

ページは制限を1回適用したあとに経路計算を呼ぶ。APIとの自己HTTP呼び出しや、クライアントでの二度目の取得をしないため二重計上を避けられる。上限時はサーバー側で`/rate-limit?source=routes`へredirectする。redirectを検索失敗としてcatchしないよう、制限判定と検索失敗処理を分離する。条件不正・検索失敗・経路なしはそれぞれサーバー描画する。

利用者間の結果や制限状態を共有キャッシュへ載せない。結果ページはリクエスト単位で処理し、同じHTTPリクエスト内で利用制限を複数回実行しない。APIのGET・POSTレスポンスと結果URLのパラメーター形式を変更しない。

### 8. スタイル変更の範囲を限定する

フォームはDaisyUIの「Fieldset with background and border」を使い、legend・labelを含めてtext-base相当を明示する。幅は利用可能な領域に合わせ、例の固定幅をそのまま移さない。既存の配色、角丸、余白、フォーカス表示を利用する。

入力画面の確定住所や注意書き、結果本文を囲う重複カードは取り除く。Nostr専用UIなど今回変更しない機能の内部スタイルまで広げない。入力の全体リセットと結果画面のリセット表現を除き、結果には「入力画面に戻る」という通常のリンクを残す。リンク内のテキストとrubyをインラインの文章として扱い、単語やルビの要素をflex / blockで別々の行に分けない。狭い幅での自然な折り返しは許容する。

### 9. RubyfulとReactのDOM更新を分離する

Rubyfulは通常の`afterInteractive`読み込み、保存済み設定による初期表示、変更監視、ON / OFF切替を維持する。ルビを無効にしたり、テストでスクリプトを遮断したりする案は採用しない。

`.ruby-text`の付与先を見直し、Rubyfulが置換するテキストとReactが更新する操作要素を分離する。共通Button全体を変換対象にする構成をやめ、ラベルのルビを保ちつつ、アイコン、ローディング表示、条件付きの子要素を変換範囲に混在させない。PDF・カレンダーとGPS、住所の確定・再編集、日時・優先条件、フォーム送信を同じ方針で扱う。例外を握りつぶす処理や旧UIへのフォールバックは追加しない。

共通ButtonはHTML要素とFragment内のテキストをラベル単位で扱い、SVG・MathML・aria-hiddenの部分木とカスタムコンポーネント内部を自動変換しない。カスタムコンポーネントのラベルは、文字列または数値を受け取る`ButtonLabel`で明示する。`ButtonLabel`はルビ変換対象の可視文字をaria-hiddenとし、基底文字をsr-onlyで提供する。動的な文字の変更ではラベルの変換範囲を置き換え、操作要素やアイコンをRubyfulのDOM置換から分離する。これは承認済みのラベル分離方針の具体化であり、検索や出力の要件は追加しない。

通常読み込み後にルビ変換が実行された状態と、ON / OFFを繰り返した状態で操作する。コンポーネントテストでは外部DOM置換後の状態更新を再現し、実ブラウザでは通常のスクリプトによる変換と動的ラベルのルビを確認する。PDF・カレンダーはボタンの存在だけでなく、既存データで出力が完了することを確認する。

### 10. 共通ボタンとルビ切替ボタンの配色

共通Buttonのprimary / secondary、アイコンのみ、joined、loading / disabledと、Rubyfulが生成するルビ切替ボタンを検証対象にする。配色は既存テーマの役割に沿って調整し、共通Buttonとルビ切替ボタン以外へスタイル変更を広げない。検索以外の共通ボタンも対象とするが、検索以外の操作を虫眼鏡に変更しない。

ライト・ダークの両テーマで、通常、hover、active、focus-visibleとルビON / OFFの算出色を実測する。通常文字は4.5:1以上、大きな文字はWCAG 2.2の定義に従って3:1以上とし、操作や状態の識別に必要なアイコン・境界・フォーカス表示は隣接色との3:1以上を確認する。`.transit-button:not(:disabled)`の`border-color: currentColor`と`.my-toggle`の文字色による装飾枠線の強制を除く。DaisyUIと既存テーマの配色を使い、識別に必要な境界だけを必要に応じて調整する。すべての枠線へ3:1を課すテストは必要な非テキストを判定するテストに改める。文字やアイコンで操作を識別できる場合の装飾枠線は対象外とするが、可視フォーカスの検証は省略しない。非アクティブな操作には1.4.3・1.4.11の例外を適用し、loading / disabledの状態通知と操作禁止も別に検証する。クラス名やテーマ変数の静的検査だけでは適合を判定しない。

基準は[WCAG 2.2の1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum)と[1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast)を使う。装飾枠線の扱いは[Understanding 1.4.11のBoundaries](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html#boundaries)に照合する。

### 11. 変更する振る舞いを先にテストする

段階入力、日時ラベル切替、router.push、クライアントでの結果fetchを前提とする既存テストは、新仕様の振る舞いを検証するものへ置き換える。フォームの実物を組み合わせたテストで、入れ子の不存在、Enterとsubmit、name / value、局所的な再編集、エラー時の保持を確認する。ソース文字列検査だけでは送信の正しさを判定しない。

サーバー結果のテストは直通・乗換・経路なし・条件不正・失敗・429を含め、APIとページの制限判定、IPの分離、二重計上がないことを確認する。Nostrは遅延・失敗・無効設定を模擬し、本文とPDF用データの独立を検証する。

### 12. devのJavaScript文字列SyntaxErrorを修正する

開発環境で観測したJavaScript文字列のSyntaxErrorは、この変更の完了までに原因を特定して修正する。既存のverification.mdに残る原因未確定の留保を、修正不要の結論として使わない。アプリと検証ハーネスのどちらにも原因を決めつけない。

`npm run dev`の実ブラウザで初回表示、結果URLへの直接アクセス、フォーム送信、Rubyful切替、PDF・カレンダー出力を実行する。pageerror、console、失敗したスクリプトURLと行・列、配信応答、スタックを採取する。ハーネスが注入するJavaScript文字列と実際の配信文字列を区別し、引用符・改行・エスケープなどのどこで構文が不正になるかを最小再現へ絞る。productionだけの成功でdevの失敗を打ち消さない。

原因を再現するテストでREDを確認してから、原因箇所の文字列生成または配信・注入処理を修正してGREENにする。例外の握りつぶし、エラーの除外、ルビ無効化は採用しない。devと`npm run build`後の`npm run start`を別々に起動し、同じ操作を実ブラウザで再検証する。通常のRubyful読み込みと保存済みON、繰り返しON / OFFを含め、SyntaxErrorが再発せず、入力から出力まで完了することを確認する。

### 13. 改定後の検証を取り直す

入力順序・最終submitの可視名・補助ボタンの幅・装飾枠線・結果の区間順序と文字サイズ・戻るリンクを、コンポーネントテストと実ブラウザの両方で検証する。devとproductionの両環境、cupcake / dark、320〜1440 CSS px、200%文字拡大と400%ズームを対象にする。DOMのクラス名だけでなく、算出サイズ、要素の位置・幅、フォーカスと読み上げ名を確認する。

既存の検証記録は過去の実行結果として保持する。改定後の適合やSyntaxError解消の証拠へ読み替えず、環境、操作、RED / GREEN、配信スクリプト、スクリーンショット、計測値、監査結果を新たに記録する。

## Risks / Trade-offs

- [ネイティブGET遷移では画面全体の移動が発生する] → 今回は通常のウェブ操作として採用する。独自の状態同期や遷移制御を追加しない。
- [サーバー検索でレスポンス開始または本文到着まで待つ場合がある] → 必要ならサーバー側で読み込み中表示を提供し、クライアントの追加検索には戻さない。
- [利用制限の抽出でAPIとページの判定がずれる] → IP識別・上限・加算・失敗を共通処理に集め、APIと結果ページを同じテスト条件で検証する。
- [JSによる日時初期化とlocalStorage復元で初期表示の一部が変わる] → 許容する。出発・到着ラベルや入力グループの有無まで変更しない。
- [カテゴリを複数開くと縦に長くなる] → ページ全体のスクロールを使い、一覧の内部スクロールを復活させない。
- [フォーム全体のライブ通知を外すと状態変化を伝え損なう] → 項目単位の通知とフォーカス移動を、キーボード・読み上げで確認する。
- [RubyfulのDOM置換とReactの状態更新が干渉する] → 動的な操作要素を変換範囲から分離し、通常読み込みと繰り返し切替後の操作・出力を回帰テストで確認する。
- [DaisyUIの標準文字サイズや余白だけではアクセシビリティ条件を満たさない] → 両テーマで算出サイズ、コントラスト、320 CSS px相当のリフロー、文字200%拡大を実測する。

## Migration Plan

1. 各作業単位で新仕様のテストを先に追加・更新し、意図した失敗を確認してから実装する。
2. 入力・共有検索ボタン・結果取得と表示を順に変更し、同じURLとAPI契約のまままとめて公開する。DBや保存データの移行はない。
3. `CategoryTabs`と`ResetButton`は利用箇所がなくなった時点で削除する。使わないクライアント取得処理も残さない。
4. 型検査、対象と全体のテスト、ESLint、アクセシビリティ監査と手動検証を行う。既存の`npm run lint`がNext.js 15のCLIと整合しない場合は直接ESLintを実行し、検査できなかった項目を隠さない。
5. リリース後に不具合があれば変更を一括で戻す。旧UIの並行実装や機能フラグは追加しない。
