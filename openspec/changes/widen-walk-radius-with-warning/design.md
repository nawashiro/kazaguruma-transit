# Design

## Context

徒歩距離は3か所で別々に求めている。経路検索は`walkLeg`を停留所ごとに呼び、目録の更新は`selectNearbyStops`を1回呼び、名前索引は距離を求めない。上限は`TRANSIT_PARAMS.DEFAULT_SEARCH_RADIUS`（500）1つで、足切りと警告の両方を兼ねている。名前索引は`data/geocode-index.json`（1.3MB）にあり、`/api/geocode`はプロセス内に1度だけ読み込む。徒歩ネットワークは`data/walk-network.json`（28,218ノード、34,813エッジ）で、`getWalkNetwork`がプロセス内に1度だけ読み込む。

実測した数字を前提にする。名前索引10,977件のうち500m以内は9,149件、500–750mは349件、750m超は1,479件。公開グラフのPlace 106件のうち500m以内は86件、500–750mは5件、750m超は15件。停留所は79件。

距離は測る地点で決まる。公開グラフの座標で測ると科学技術館535m、北の丸公園573m、国立国会図書館554m、千鳥ヶ淵公園590m、千鳥ヶ淵戦没者墓苑621m。現在の索引の座標で測ると同順に537m、540m、733m、600m、478mになる。索引と目録は座標が一致しないため、本文ではどちらの座標で測った値かを添える。

## Goals / Non-Goals

**Goals:**

- 徒歩距離の算出を1か所に集約し、経路検索・目録・地点検索が同じ値を返す。
- 地点の選択段階で遠さを示し、選べない理由を経路検索の前に伝える。
- 徒歩距離の上限と警告線を別の定数に分ける。

**Non-Goals:**

- 経路の選択順位を変えない。500mを超える徒歩区間は、到着時刻の比較で不利にしない。
- 徒歩ネットワークの生成条件を変えない。広場（OSMの`area=yes`）を面として扱わないのはCoMapsの徒歩モデルと同じ判断であり、面を捨てても周囲の線の歩道で繋がる。公園が遠く出るのは徒歩網の穴ではなく、代表点と入口の隔たりである。
- 出発地の徒歩距離から経路探索の時刻を変えない。既存の徒歩時間の使い方を保つ。

## Decisions

### 距離の正本を1つの関数に寄せる

`src/lib/transit/stop-access.ts`を追加し、`measureWalkAccess(stops, lat, lng, graph)`を置く。返り値は最寄り停留所までの徒歩距離（メートル）と、その停留所のID。実装は停留所の座標へ`snapToNetwork`し、停留所を種にした多点ダイクストラを1回回す。全停留所の座標の距離場をプロセス内に1度だけ作り、以後は候補の座標の最寄りノードの値とスナップ距離で引く。多点探索は`walk-network.ts`の`searchFromMany`に置き、`walkLeg`と同じ距離の規則を保つ。実測で距離場の構築6.4ms、候補5件0.18ms、名前索引10,977件の一括計算132ms。

停留所ごとに`walkLeg`を呼ぶ案は採らない。停留所79件×候補10,977件で1回の探索が4msかかるため、索引全体で数分かかる。

`walkLeg`を使い続ける案は採らない。目録の更新と地点検索で同じ値を出すために、探索の起点と打ち切り条件を揃える必要がある。

**両端が同じノードに接続するときの距離**は`walkLeg`と同じ規則にする。同じノードなら2地点間の直線距離、違うノードなら接続区間の和。この規則を関数の内側に閉じ込める。

### 定数を2つに分ける

```ts
export const TRANSIT_PARAMS = {
  /** 出発地・目的地から乗り降りする停留所まで歩ける距離の上限（メートル）。 */
  MAX_WALK_TO_STOP_METERS: 750,
  /** この距離を超える徒歩区間に警告を出す（メートル）。 */
  WARN_WALK_TO_STOP_METERS: 500,
  WALKING_SPEED_KM_H: 3,
  ...
};
```

`DEFAULT_SEARCH_RADIUS`は削除する。同じ値を足切りと警告の2つの意味で使い、`/1000`したキロメートル単位で持ち回っていたため、単位の取り違えが起きやすい。名前を距離の意味にし、単位をメートルに統一する。二重実装を残さないという憲章のKISSに従い、旧名の別名は置かない。

### 遠さの段階は2つ

徒歩距離`distance`に対して、`distance <= 500`を通常、`500 < distance <= 750`を「バス停から遠い」、`750 < distance`を「バス停から遠すぎ」とする。境界の扱いは既存の「上限ちょうどは含める」を保つ。段階の判定は`walkAccessLevel(distanceMeters)`として距離の算出と同じモジュールに置き、画面とAPIが同じ関数を使う。

### 目録は距離を持ち、ビルドは測り直さない

`DestinationCatalogEntry`へ`walkToStopMeters: number`を加える。目録の更新は候補にした時点の距離を書く。`routeDestinations`のartifactはこの値を`walkMeters`として持ち、入力画面の施設一覧はこれを表示する。ビルドで測り直さないのは、`location-catalog` specの「ビルドで徒歩圏を再計算しない」を守るため。

目録の更新は停留所を1回読み、`measureWalkAccess`の距離場を1度作れば、全recordを測れる。いまはrecordごとに`selectNearbyStops`を呼んでおり、record106件で停留所79件ずつ探索している。

### 地点検索の距離は実行時に測る

`/api/geocode`は候補を最大5件返す。5件を測るのに0.7msしかかからないため、前計算して索引へ格納しない。索引の再生成にOSM抽出133MBの取得が必要になり、徒歩ネットワークとの鮮度を揃える検査も要るため、実行時計算の方が単純である。

徒歩距離を求められない場合は`walkMeters`を省略し、検索は成功のまま返す。`location-search` specの「索引を読み込めないときは失敗を返す」は索引の話であり、徒歩ネットワークの失敗で検索全体を落とす理由はない。停止の可否でいえば、地点を選べることより遠さが分かることの方が重要度が低い。

**同じ施設が2つの距離を持つことを許す。** 施設一覧の距離は目録が持つ公開グラフの座標から測り、名前検索の距離は索引が持つ座標から測る。索引の座標はOSM名とartifact名を街区で束ねた平均であり、公開グラフの座標と一致しない。実測では掲載36件のうち5件が50m以上ずれ、最大は岩本町ほほえみプラザの2m（索引）と77m（目録）で、同名の停留所が索引側の座標に近いためである。警告の段階が変わるものは0件だった。

測る地点が違えば距離も違うのが正しい。索引の候補は索引の座標を指しており、利用者はその地点を選ぶ。目録の一覧は公開グラフの座標を指す。両者を同じ距離に揃えるには、どちらかの座標を捨てるか、索引に目録のIDを持たせて座標を上書きする必要がある。後者は`location-search`の「索引だけで検索する」前提を崩し、索引の生成が目録に依存する。ずれが警告の段階に響かない以上、座標ごとに測る方を採る。

### 選択不能はボタンにせず、灰色で示す

`disabled`のbuttonはフォーカスを受けず、読み上げの対象にもならない。遠すぎる候補は`<li>`の中で、ボタンではない文章として名前・住所・理由を並べる。選べる候補だけをbuttonにする。これで、キーボードでたどったときに選べない候補が操作対象として混ざらず、理由は文章として読める。

灰色にするだけでは選択できないことが伝わらないため、項目全体の地色を`bg-base-300`に変え、枠を破線にし、`cursor-not-allowed`を付ける。`aria-disabled`も添える。文章として残した項目が「押せるのに押せない」と読まれないようにするための、3つの手掛かりである。

### 距離の数値は結果画面の徒歩区間だけに出す

徒歩距離は補助的な情報であり、入力の途中では名前と住所を読む妨げになる。バッジは文字（「バス停から遠い」「バス停から遠すぎ」）だけで足りるため、検索候補・施設一覧・確定済みの地点にはメートルを併記しない。メートルを出すのは、検索の結果として徒歩区間を示す結果画面だけにする。行程を振り返る場面では「どれくらい歩くか」が判断の材料になるが、地点を選ぶ場面ではバッジで足りる。

バッジは`badge badge-lg`の既定のパディングに戻す。`p-2`と`h-auto`で膨らませると、ボタンと見分けが付かなくなるためである。`badge-lg`は文字16pxを保ちつつ、高さと左右の余白はdaisyUIの既定に任せる。

### 結果画面は徒歩区間ごとに距離を出す

`RouteResultViewModel`へ`originWalkMeters`と`destinationWalkMeters`を加え、`IntegratedRouteDisplay`が「徒歩で移動(Googleマップ)」の直下に`(バス停から遠い) 537m`の形で描く。既存の`originStop.distance`は直線距離（キロメートル）であり、徒歩距離ではない。混用しないよう、新しい欄はメートルの整数にして名前で区別する。

`NearbyStop`へは`walkingDistanceMeters`を加えない。`Journey.walkingDistanceKm`は総徒歩距離のまま残し、区間ごとの値はview modelで持つ。`Journey`はAPI契約であり、合計しか使っていない現状で区間を足すと、APIの消費者に意味の重複を押し付ける。

### 遠すぎる地点の結果表示

`TransitResponse`の`data.message`は既にあるが、結果画面は`type === "none"`のとき固定文を出している。`RouteResultViewModel`へ`blockedBy?: { field: "origin" | "destination"; meters: number }`を足し、`IntegratedRouteDisplay`が経路なしの代わりに「目的地はバス停から939m離れています。バス停から15分以内の地点を選んでください」を出す。停留所までの距離が上限を超えたことを、経路の不在と区別する。

## Risks / Trade-offs

- **[遠い施設が選べなくなる]** → 750mを超える地点は、いま選べるものも選べなくなる。東京駅（939m）、帝国劇場（1,776m）が該当する。地点の名前と住所は一覧に残し、灰色と理由で選べないことを示す。リリースノートに挙動の変更として書く。
- **[代表点が入口から離れた地物が遠く出る]** → 公開グラフの座標は施設の代表点であり、大規模な公園では入口から数百m離れる。徒歩網は地物の内側まで通っている（皇居東御苑の代表点の周囲200mに507ノード、代表点から北桔橋門まで園内を762m歩ける）。距離の算出ではなく座標の持ち方の問題であり、上流の`nawashiro/chiyoda_city_main_facilities#79`で代表点の見直しを依頼した。この変更では距離の算出も徒歩網の生成条件も変えない。

  公開グラフのPlace 106件について、代表点の徒歩距離と、地物の境界上で最も停留所に近い点の徒歩距離を比べた。差が100m以上の11件を示す。代表点の徒歩距離から境界の徒歩距離を引いた値を短縮とする。

- **[同じ施設が2つの距離を持つ]** → 施設一覧は目録の座標、名前検索は索引の座標から測るため、掲載36件のうち5件が50m以上ずれる。最大は岩本町ほほえみプラザの2mと77m。警告の段階が変わるものは0件であり、ずれは段階の境界をまたがない。揃えるには索引の生成を目録へ依存させることになり、`location-search`の前提を崩すため採らない。段階が変わるずれが出た場合は、索引の座標か目録の座標のどちらが正しいかを上流で確かめる。
- **[距離場の初期化コスト]** → `/api/geocode`の初回要求で6.4msを加える。索引の読み込み（1.3MB）より小さく、許容する。距離場は同期で組み立て、停留所と徒歩ネットワークの署名を鍵にモジュール内へ残す。Node.jsは1つの要求を最後まで走らせてから次を処理するため、同じ鍵で二重に作ることはない。
- **[目録の距離が古くなる]** → 停留所や徒歩網が変わった後に目録を更新しないと、一覧の距離が古いまま出る。経路検索の結果と食い違う。`docs/how-to/update-destinations.md`に、徒歩網を更新したら目録も更新する手順を書く。
- **[APIの応答が増える]** → `/api/geocode`の候補に`walkMeters`が加わる。省略可能な欄なので、既存の消費者の動作は変わらない。

## Migration Plan

1. 定数と`stop-access.ts`を追加し、経路検索・目録・地点検索を新しい算出へ切り替える。この時点で`DEFAULT_SEARCH_RADIUS`を削除する。
2. 目録の形式に`walkToStopMeters`を足し、`npm run update-destinations`で`data/destinations.json`を再生成する。形式を変えたため、旧い目録は検証で落ちる。再生成を必須の手順としてリリース手順に置く。
3. `npm run build`で場所artifactを再生成する。`routeDestinations`に`walkMeters`が入り、場所一覧が86件から91件へ増える。
4. 場所artifactを読む`npm run update-geocode-index`を実行する。索引は10,977件のままで、座標が動くのは4件（国立公文書館、国立国会図書館、神田さくら館、千鳥ヶ淵戦没者墓苑）である。千鳥ヶ淵戦没者墓苑は種別も`other`から`park`へ変わる。科学技術館、北の丸公園、千鳥ヶ淵公園は索引の座標が変わらない。座標が動くと徒歩距離の帯も変わりうるが、帯が変わったのは千鳥ヶ淵戦没者墓苑の478m→664m（圏内→遠い）だけであった。
5. 新しい5件のうち施設一覧に載せるものを選び、`includeInRouteForm`を`true`にして`npm run build`を再実行する。選ばなければ施設一覧は36件のままである。
6. 画面を切り替える。ロールバックは、定数と目録の形式を戻して再生成する。目録は生成物なので、旧い版をそのまま戻せる。
