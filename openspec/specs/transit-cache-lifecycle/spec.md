# transit-cache-lifecycle Specification

## Purpose

交通DBをGTFSから再生成できるキャッシュとして扱い、起動時の設定とスキーマに対応する時刻表で配信を始める。古いDBの手動削除を不要にし、再生成の失敗時には配信を開始しない条件を定める。

## Requirements

### Requirement: 起動ごとの交通DB再生成

システムは`npm run dev` と `npm start` の実行ごとに、設定された交通DBを破棄し、現在のスキーマと設定されたGTFSから再生成しなければならない（MUST）。既存DBの内容やスキーマの互換性によって取込をスキップしてはならない（MUST NOT）。

#### Scenario: データが入った既存DBで起動する

- **WHEN** 古い時刻表が入ったDBがあり、設定されたGTFSの時刻表を変更して起動する
- **THEN** 再生成後のDBで変更後の時刻表を提供し、旧GTFSだけにあったデータは残さない

#### Scenario: 旧スキーマまたは壊れたDBで起動する

- **WHEN** 旧スキーマのDBまたはSQLiteとして読み取れないファイルが設定先にあり、削除と再生成が可能な状態で起動する
- **THEN** 既存ファイルの読取やデータ移行を必要とせず、現在のスキーマとGTFSで起動する

#### Scenario: DBが存在しない

- **WHEN** 設定されたDBとその親ディレクトリが存在せず、作成権限がある状態で起動する
- **THEN** ディレクトリとDBを作成し、GTFSを取り込んで起動する

### Requirement: 検証完了後の配信開始

システムはスキーマ作成、GTFS取込、取込結果の検証が成功してから配信を開始しなければならない（MUST）。検証では事業者、路線、停留所、便、停車時刻と、運行日または運行日例外のデータが存在し、レート制限の保存領域を利用できることを確認しなければならない（MUST）。

#### Scenario: 再生成が完了するまで配信を待つ

- **WHEN** GTFSの取込または検証が進行中である
- **THEN** アプリの配信処理を開始しない

#### Scenario: 運行日例外だけで運行日を定義する

- **WHEN** 必須の交通データがそろい、運行日の定義は運行日例外だけに存在し、レート制限の保存領域も利用できる
- **THEN** 検証を成功として配信を開始する

### Requirement: 再生成失敗時の起動中止

システムは設定の読込、DB削除、スキーマ作成、GTFS取得・取込、検証のいずれかが失敗した場合、非ゼロの終了状態で起動を中止しなければならない（MUST）。旧DBや不完全な取込結果で配信を開始してはならない（MUST NOT）。

#### Scenario: 取得元が応答しない

- **WHEN** 既存DBがあっても、設定されたGTFSのURLから取得できない
- **THEN** 起動を失敗とし、旧DBによる配信は開始しない

#### Scenario: 取込後に必須データが欠ける

- **WHEN** GTFS取込が終了しても、検証対象の必須データが欠けている
- **THEN** 非ゼロの終了状態を返し、配信を開始しない

#### Scenario: 失敗後に再起動する

- **WHEN** 前回の取込で不完全なDBが残り、取込元の問題を解消して再起動する
- **THEN** 不完全なDBを破棄して再生成し、検証成功後に配信を開始する

### Requirement: レート制限カウンターの寿命

システムは交通DBの再生成時に、同じDB内のAPIレート制限カウンターをリセットしなければならない（MUST）。

#### Scenario: 制限に達した利用元が再起動後にアクセスする

- **WHEN** ある利用元のカウンターを記録した後にアプリを再起動する
- **THEN** その利用元のカウンターは初期状態となり、再起動前の件数を引き継がない

### Requirement: 設定先と再生成対象の一致

システムはスキーマ作成、GTFS取込、アプリの参照先に同じ `transit-config.json` の `sqlitePath` を使わなければならない（MUST）。破棄する対象はそのDBと付随するSQLiteファイルに限定し、設定ファイルとGTFSの入力データを保持しなければならない（MUST）。

#### Scenario: 標準以外のパスを使う

- **WHEN** 独自の相対パスまたは絶対パスを `sqlitePath` に設定して再生成する
- **THEN** 設定先のDBだけを再生成し、別のDB、設定ファイル、ローカルGTFS入力は変更しない

### Requirement: 明示的なキャッシュ再生成

システムはアプリ停止中の `npm run import-gtfs` で、起動時と同じDB破棄・スキーマ作成・GTFS取込・検証を実行しなければならない（MUST）。成功時はゼロ、失敗時は非ゼロの終了状態を返さなければならない（MUST）。

#### Scenario: 既存DBを明示的に再生成する

- **WHEN** アプリを停止して、データが入ったDBに対して `npm run import-gtfs` を実行する
- **THEN** 既存データを再利用せず現在の入力から再生成し、検証結果に応じた終了状態を返す

### Requirement: 時刻表更新の反映時期

システムは稼働中のGTFS入力の変更を自動取込せず、次の起動時に反映しなければならない（MUST）。

#### Scenario: 稼働中に入力を更新する

- **WHEN** 稼働中にGTFS入力を更新し、その後アプリを停止して再起動する
- **THEN** 再起動前は取込済みの時刻表を提供し、再起動後は更新された入力から再生成した時刻表を提供する

### Requirement: ビルドと交通DBの分離

システムは`npm run build` で稼働用の交通DBを作成・破棄・更新せず、GTFSの取得成功をビルドの条件にしてはならない（MUST NOT）。

#### Scenario: ビルド時にGTFSを取得できない

- **WHEN** ビルドに必要な他の入力がそろい、GTFS取得元だけが利用できない状態で `npm run build` を実行する
- **THEN** GTFS取得は実行せず、交通DBとカウンターを変更せずにビルドを完了できる
